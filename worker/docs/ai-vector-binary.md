# AI vector data and binary provenance

AI profile 1.2.0 adds `N8N_AI_VECTOR_DATA`. It inspects possible document and query transfers from definitions, without loading files, decoding attachments, calling a provider, or executing a node, expression, Code body or generated tool argument. Original assessment status and operational authorization remain separate.

## Fixed definition profiles

The reviewed additions are Pinecone vector store 1; Supabase vector store 1.3; OpenAI embeddings 1/1.1/1.2; Gemini embeddings 1; default document loader 1/1.1; recursive character splitter 1; MongoDB chat memory 1/1.1; Groq chat model 1; Wikipedia tool 1; and generated DateTime 2, Crypto 1 and RSS Read 1.2 tool wrappers. Other versions keep unsupported diagnostics. Supporting a typed connection does not claim full request or runtime semantics. In particular, RSS requests retain a separate request-content gap and a dynamic destination remains a review candidate.

Vector mode controls the contract. `retrieve` produces `ai_vectorStore`, `retrieve-as-tool` produces `ai_tool`, and `insert` consumes one `ai_document` and one `ai_embedding` producer. Each accepts output zero and input zero only; duplicates, incompatible roles, disabled producers and unknown versions do not become covered routes. Groq occupies the second model input only when the Agent's existing `needsFallback` setting enables it. Reversed Agent-to-model/parser edges in frozen examples 7622 and 7643 remain unresolved rather than being repaired.

## Document and query transfers

For insertion, the loader processes the vector store's main input. `jsonMode=allInputData` retains all possible JSON document classes. `expressionData` uses only its declared `jsonData`; an unrelated secret in the main input does not become a selected public document's content. Strings remain strings and are not parsed again as expressions inside data. Loader metadata is evaluated separately: it reaches storage, not the embedding text. Known source classes and unknown remainders survive serialization and splitting. Source evidence uses node hashes and fixed structural locations, never document text, metadata keys, addresses or secret values.

The rule reports document-to-embedding and document-to-vector-store candidates separately. It also traces fixed `load` prompts and possible initiating prompts through reviewed retriever/tool connections. Generated queries and returned documents remain unknown. JSON pointer selection, custom or invalid selectors, unsupported splitters/rerankers, update semantics, unknown connections and analysis limits retain specific gaps. Unknown modes or future store versions are not treated as supported operations.

Embedding policies use the embedding node key and `ai_model` sink. Storage policies use the store node key and `ai_vector_store` sink. An explicit reviewed OpenAI embedding `options.baseURL` may establish its configured origin; credentials and runtime routing are not read. Store endpoints remain unresolved. Policy absence is a configuration caution. With a supplied policy, a known forbidden data class still yields a denial candidate when the endpoint is unknown; unknown-only content cannot become allowed. These statements concern supplied policy evaluation, not observed transmission or leakage.

## Binary absence is a narrow proof

`binaryInputProvenance` returns `none`, `possible` or `unknown` and bounded source dependencies. It describes possible `item.binary` provenance, not actual file bytes, a particular binary-property key, MIME type, file existence or successful execution.

`none` requires a reviewed Set removal configuration without binary assignments, or a single parse-only Code return of fresh constant JSON-only item literals. Code with input references, calls, spreads, accessors or preceding statements does not qualify. Fixed IF/Switch/no-op definitions can preserve an earlier result only when their parameter expressions meet a bounded read-only subset. Unreviewed calls, assignments, updates, dynamic collections/modes, malformed options, bad input ports, error outputs and pinned node output prevent an absence proof. Pinned data is never promoted to observed runtime data. Unknown transforms retain earlier binary and JSON-to-file dependencies.

Convert to File 1/1.1/1.2 supports `toJson` and fixed dotted `sourceProperty` selection for `toText`/`toBinary`. Other conversions preserve a whole-input candidate plus an unsupported gap. This does not infer whether bytes decode successfully or whether a produced file is accepted by a model. Read File 1 is a possible producer with unknown contents; other service responses stay unknown. Generic connector binary support is not claimed.

Agent binary options being enabled by default no longer imply a missing file. Proven absence removes that potential input. A possible producer retains content uncertainty; an unknown producer also retains a provenance gap. Chain `imageBinary` messages and binary document loaders use the same distinction, including a missing-input gap after proven stripping. Turning off Agent binary passthrough does not change its text prompt or other context.

The binary walk limits depth to 24, visits to 128, incoming edges to 32 and retained dependencies to 64. Read-only parameter inspection limits visits to 2,048, depth to 32, parameter nesting to 16, strings to 65,536 characters and templates to 32 expressions. Fresh Code proofs cap syntax visits at 1,024 and items at 32. Vector traversal limits depth to 8 and definitions to 32; document/embedding fan-in is limited to 8 and metadata inspection to 128 values. Limit/cycle diagnostics retain unknown and cannot become completion notices.
