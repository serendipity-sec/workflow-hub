# 개발 목표와 실행 계획

> 상태: 보안 기능은 미구현이며 세부 계약은 팀 검토 대상이다. #8·#10의 DB 기반과 버전 정책 위에서 1차 구현 범위와 선택적 고도화를 5절에 구분한다. 고도화 목록은 일정·도입 약속이나 1차 완료 조건이 아니다. 조사 근거와 성능 측정 결과를 구분한다.

## 1. 제품 목표

다른 사람이 만든 n8n 워크플로를 가져와 사용하려는 사람이 동작, 위험 근거, 사용 조건을 이해하고, 수정본의 검사 이력을 비교한 뒤 특정 버전을 선택할 수 있게 한다.

기존의 개인 비공개 업로드·버전·다운로드 흐름을 기반으로 다음 경험을 연결하는 것을 제안한다.

1. JSON을 업로드하고 불변 버전을 생성한다.
2. 비동기 검사 결과에서 확인된 설정, 위험 경로, 분석하지 못한 부분을 확인한다.
3. 노드·필드·데이터 흐름을 통해 근거를 이해한다.
4. 수정 안내에 따라 고친 파일을 업로드해 새 버전을 만든다. 자동 수정안 생성·적용은 선택적 고도화다.
5. 재검사와 보안 변화 비교로 수정 효과와 새 위험을 확인한다.
6. 정책과 사용 조건에 맞는 특정 버전을 공개·다운로드·재사용한다.

서비스 배포를 위해 Supabase PostgreSQL과 실행 환경을 준비한다. 최초 지원 목록과 공개 정책은 해당 구현 전에 결정한다. 광범위한 분석·자동 수정·운영 환경 연동을 기다리지 않고, 제한된 지원 범위에서 이 흐름을 먼저 완성한다.

### 차별화 근거와 검증

n8n 공식 심사·감사·버전 리뷰·패키지, n8n 전용 카탈로그·마켓, 공개 검사기의 흐름 분석·보안 변화 비교를 비교 기준으로 삼는다. 공개 취약 템플릿, 고의 악성 JSON, 악성 커뮤니티 패키지, 런타임 CVE는 다른 근거로 관리한다. 기존 보안 기능이 없다는 주장이나 경고 수를 취약률로 바꾸는 주장을 사용하지 않는다.

검증할 가설은 근거 이해, 실제 작업 값·검증 조건·분기의 분석 기여, 사용 정책에 따른 판단, 보안 변화 파악, 정상 동작을 유지하는 수정, 검사한 파일의 정확한 선택이다. 조사한 기능의 존재만으로 우리 효과를 입증하지 않는다. 플랫폼·도구·사례별 출처와 한계, 해결 범위, 비교군 A~D 및 사전 평가 계획은 [DIFFERENTIATION.md](DIFFERENTIATION.md)에서 관리한다. 제품 구현, 도구 비교, 사용자 평가의 결과를 각각 기록한다.

## 2. 기존 계획과의 관계

이전 계획은 4명이 9~10일 동안 개인 업로드·수정 계보·다운로드 데모를 만드는 기반 작업이었다. 보안 규칙·자동 수정·공개 공유는 당시 필수 범위에서 제외했다.

이번 문서는 그 기반 위에 보안 검사와 버전 활용을 핵심 사용자 흐름으로 추가하는 확장안이다. 이전 일정은 기반 작업의 이력으로 보존하며 새 범위의 기한으로 재사용하지 않는다. 새 일정과 담당자는 단계별 범위·완료 조건을 팀이 검토한 뒤 정한다.

이후 [#8](https://github.com/serendipity-sec/workflow-hub/issues/8)·[#10](https://github.com/serendipity-sec/workflow-hub/pull/10)에서 기존 리비전 트리를 워크플로별 버전 이력으로 변경하고 PostgreSQL·Flyway 저장 기반을 구현했다. 보안 검사는 이 최신 모델의 정확한 버전과 파일에 연결하며, 부모 트리를 다시 도입하지 않는다.

이 표는 실제 클라우드 자원 확인이나 새 테스트 실행 결과를 대신하지 않는다. 구현·연동 완료 여부는 코드, 검사 결과, 배포 기록에 따라 갱신한다.

현재 앱은 단일 datasource로 시작 시 마이그레이션도 실행한다. 업로드와 버전 등록은 S3의 별도 객체 키에 파일을 저장하고 서비스에서 소유권을 확인한다. 버전별 원본 파일 SHA-256·크기는 서버가 저장하는 바이트로 계산해 기록한다(V6, 이전 버전은 NULL). 검사·공개 상태와 파생 관계는 후속 구현이다.

## 5. 단계별 구현 순서 제안

### 1차 구현 범위

우선 목표는 **업로드 → 제한된 정적 검사 → 근거 확인 → 수정본 업로드 → 새 버전 재검사 → 보안 변화 비교 → 특정 버전 공개·다운로드**를 연결하는 것이다. 최초 분석 대상은 대표 위험 경로 1~2개로 좁힌다. 구체적인 노드·버전·작업·표현식과 위험/정상/미지원 사례는 분석 구현 전에 지원 목록으로 고정한다. 아래 범위 구분은 제품 코드가 구현됐다는 뜻이 아니다.

| 영역           | 1차에 구현할 범위                                                                                                        | 1차 완료에서 요구하지 않는 것                                            |
| -------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| 저장·검사 기반 | 소유권 확인, 비공개 원본·수정본, 불변 버전·실제 파일 해시, 비동기 작업·실패 처리                                         | 새 버전 트리, 의미 검색, 외부 원본 자동 수집                             |
| 분석·근거      | 선택한 1~2개 위험 경로의 입력·사용 필드·관련 검증 조건과 근거 표시. 직접 노드 참조·무관한 IF를 포함한 반례와 미지원 표시 | 모든 검사 유형·노드의 지원, 임의 Code와 복잡한 결합·분기의 완전 분석     |
| 수정·비교      | 위치·수정 방향 안내, 사용자가 고친 파일의 새 버전 생성, 같은 기준 재검사, 위험·미확인 변화 비교                          | 자동 패치 생성·적용, 모든 수정의 기능 보존을 자동 보증                   |
| 사용 조건·공개 | 확인한 조건과 사용자 선언 구분, 위험·미확인 처리 정책 결정, 선택한 버전과 정제된 결과의 공개, 출처 표시·다운로드 일치    | 세밀한 조직별 정책 언어, 실제 n8n 실행 차단·운영 상태 감시               |
| 검증           | 선택한 경로의 위험/정상/미지원 사례, 수정 후 정상 기능, 인가·무결성·작업 실패, 좁힌 동일 사례의 기존 도구 비교           | 전체 25개 사례의 모든 변형, 모든 경쟁 도구·H1~H5의 대규모 실험 동시 완료 |

첫 내부 통합 시연은 비공개 흐름으로 진행할 수 있다. 그러나 특정 버전 공개·재사용·다운로드는 1차 제품의 후반 범위이며 선택적 고도화로 미루지 않는다. 1차 재사용은 공개한 정확한 버전의 다운로드로 충족한다. 플랫폼 안에서 타인 파일을 내 워크플로로 복제하고 출처 관계를 관리하는 파생 기능은 선택적 고도화이며, 도입할 때 #8의 독립 워크플로 `v1` 규칙을 적용한다. 공개 허용·검토·차단, 미지원 처리, 출처·재배포·철회 정책을 공개 기능 구현 전에 정하고 검증한다. 개인 비공개와 권한·마스킹 경계를 먼저 확보한다.

초기 비교는 선택한 사례와 적용 가능한 기존 도구를 고정해 관측 결과를 남기는 데 초점을 둔다. 사용자 판단 개선·탐지 우월성·수정 성공률을 주장하려면 별도의 사전 평가 계획과 해당 비교 실험이 필요하다. 고급 기능이나 대규모 연구 평가의 미완료를 1차 구현 실패로 취급하지 않으며, 반대로 기능 시연만으로 성능 우위를 선언하지 않는다.

### 처음부터 보존할 확장 기반

- 원본·수정본의 불변 버전과 실제 파일 해시, 수정 기준/결과 버전의 명시적 연결을 남긴다. 자동 수정기가 없어도 수동 수정본의 관계를 기록한다.
- 검사마다 대상 버전·해시, 결과 계약·엔진·규칙·노드 어댑터 버전, 노드·필드·경로 근거, 분석 범위·미지원 사유를 기록한다. 분석기 교체와 재검사는 새 실행으로 남기고 과거 결과를 덮어쓰지 않는다.
- 실행 상태, 분석 범위, 정책 판단, 공개 상태를 분리한다. 초기의 단순 공개 정책도 적용한 정책 버전과 판단 근거를 기록한다.
- 외부 출처·의존성·환경 정보는 사용자 선언/확인/미확보를 구분할 수 있게 한다. 초기에는 미확보를 명시할 수 있으면 되며 자동 수집기를 요구하지 않는다.
- 노드 해석과 외부 도구 결과를 워커의 어댑터에서 정규화한다. 지원 목록·계약 버전·합성 반례를 함께 관리하고, 새 기능에 필요한 필드와 스키마는 후속 마이그레이션으로 추가한다. 확장 가능성을 이유로 모든 미래 테이블·플러그인 체계를 미리 만들지 않는다.

### 기회가 있을 때 검토할 선택적 고도화

아래 항목은 시간·인력·사용자 요구와 비교 실험의 필요성이 확인될 때 별도 이슈로 채택한다. 순서·일정·구현을 약속하지 않으며 1차 공개의 선행 조건으로 삼지 않는다.

### PostgreSQL 후속 운영 검증

Spring JDBC·PostgreSQL 드라이버·Flyway와 `workflow_hub` 스키마는 이미 도입됐다. 현재 연결 계정은 앱 시작 시 마이그레이션에도 쓰인다. 운영에서는 런타임 최소 권한과 마이그레이션 역할 분리를 보강할 수 있으나 아직 구현·검증된 상태로 표시하지 않는다.

- 기존 PostgreSQL 통합 테스트의 빈 DB·버전 중복·외래 키 검증을 유지한다. 새 마이그레이션에는 기존 DB 업그레이드와 재시작 시 중복 적용 방지 등 변경에 필요한 검증을 추가한다.
- 역할 분리를 도입하면 마이그레이션 계정의 스키마 변경, 런타임 역할의 정상 접근·DDL 거부, 연결·마이그레이션 실패 처리를 확인한다.
- 개발용 Supabase에서 배포 환경에 맞는 연결 경로, 서버 인증서를 검증하는 TLS, 역할별 권한을 확인한다. 로컬과 실제 개발 환경의 결과를 각각 기록한다.
- 비밀값 없이 설정과 확인 절차를 [SETUP.md](SETUP.md)에 정리한다.

실제 스키마는 구현 이슈에서 추가하는 마이그레이션을 기준으로 한다. 구현 API 명세는 코드와 함께 컨트롤러의 OpenAPI 어노테이션에 반영한다.

## 7. 완료를 판단하는 기준

다음은 5절의 1차 지원 범위에 적용하는 완료 조건이다. 보안 설계의 전체 검사 유형·검증 목록은 확장 시에도 사용하는 카탈로그이며 전체 항목의 구현을 1차 완료와 동일시하지 않는다.

- 버전 파일과 검사 대상이 같은 바이트임을 서버에서 확인한다.
- 버전·결과·수정안·다운로드를 다른 사용자 식별자로 요청해도 접근할 수 없다.
- 검사 실패·시간 초과·필수 미지원 경로를 문제 없음으로 표시하지 않는다.
- 탐지 결과는 노드·필드와 근거 수준을 포함하고 비밀정보가 마스킹된다.
- 지원 범위의 정상·위험·미지원 합성 사례에서 기대 결과를 확인한다.
- 같은 사례에서 기존 탐지와 자체 분석의 추가 탐지·오탐·미탐을 기록한다.
- 근거 화면·보안 변화·수정 흐름의 정상/실패 경로를 검증한다. 사용자 판단 개선이나 조치 효과를 주장하는 단계에는 별도 사용자 평가를 수행하며, 1차 기능 완료와 평가 완료를 구분한다.
- 수정 후 같은 규칙 기준으로 비교하고, 지원 테스트에서 원래 업무 동작을 확인한다.
- 검사 저장과 정책 평가 사이의 중단을 복구하며, 평가 미완료·실패·누락 상태에서 공개하지 않는다.
- 공개 파일과 검사 파일이 일치하며 다른 비공개 버전·원본·결과가 자동 노출되지 않는다. 다운로드 JSON의 민감정보 노출 검토를 별도로 완료하고, 수동 검토의 대상·범위·근거도 정확한 버전·해시에 연결한다.
- 외부 출처·의존성·환경 정보의 선언과 확인 근거를 구분하고, 다운로드 이후 수정·운영 상태를 확인한 것처럼 표시하지 않는다.
- 실제 외부 연동과 배포에서 확인하지 못한 사항을 완료 보고에 남긴다.

검사 품질은 항목별 오탐·미탐과 분석 불가 범위를 분리해 확인한다. 발견 개수나 하나의 안전 점수로 품질을 판단하지 않는다. 고정된 정확도·성능 목표는 평가 데이터와 실행 조건을 정한 뒤 합의한다.
