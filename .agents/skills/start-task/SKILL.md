# start-task

입력: 사람이 직접 생성한 GitHub 이슈 번호. 예: `/start-task 42`

이 스킬은 GitHub에 아무것도 쓰지 않는다. 이슈 생성·댓글·push는 사람이 한다.
작업 시작과 구현 단계에서는 로컬 커밋을 만들지 않고 변경을 작업 트리에 유지한다. 로컬 커밋은 `finish-task`에서 필수 검사와 리뷰를 마치고 미해결 문제가 없을 때만 생성한다.

## 1. 이슈 번호 확인

- 번호가 없으면 멈춘다. 사람에게 `개발 작업` 템플릿으로 이슈를 만들고 번호를 넘겨달라고 요청한다.
- AI가 이슈를 대신 만들거나, 번호 없이 대화 내용만으로 작업을 시작하지 않는다.

## 2. 이슈 읽기

```bash
gh issue view <번호> --json number,title,state,labels,body,comments
```

- `gh`를 쓸 수 없으면 사람에게 이슈 본문을 붙여달라고 요청한다.
- 이슈가 닫혀 있으면 멈추고 확인한다.
- 다음 항목이 있는지 확인한다: 목적, 작업 범위와 제외 범위, 완료 조건과 검증 방법, 결정 사항.
- 비어 있거나 해석이 둘 이상 가능한 항목은 질문 목록으로 정리해 사람에게 묻고 멈춘다.
  답을 받으면 사람이 이슈에 기록하도록 요청한다. AI가 추측으로 채우지 않는다.

## 3. 작업 트리와 브랜치

```bash
git status --short --branch
git fetch origin main
```

- 커밋되지 않은 변경이 있으면 멈추고 사람에게 처리 방법을 묻는다. 임의로 stash·삭제하지 않는다.
- `origin/main`에서 브랜치를 만든다: `git switch -c <type>/<번호>-<짧은-설명> origin/main`
  - type은 예정 PR 제목의 type과 같다. 설명은 영어 소문자와 `-`만 사용한다.
- 같은 이슈 번호가 정확히 일치하고 이름이 작업과 관련된 기존 브랜치는 접두사가 있어도 그대로 사용한다. `git merge-base --is-ancestor origin/main HEAD`와 `git log --oneline origin/main..HEAD`로 최신 main 포함 여부와 관련 없는 커밋이 없는지 확인한다. 다른 브랜치를 재사용할 때는 그 브랜치를 기준으로 확인한다. 번호가 다르거나 관련 없는 커밋이 있거나 최신 main을 포함하지 않으면 새로 만들지 않고 사람에게 처리 방법을 묻는다.

## 4. 문서 읽기

루트 `AGENTS.md`, 작업 영역의 `frontend/AGENTS.md`, `backend/AGENTS.md` 또는 `worker/AGENTS.md`, `docs/PLAN.md`, `docs/ARCHITECTURE.md`, 관련 API 컨트롤러의 OpenAPI 어노테이션을 읽는다.
이슈 내용이 이 문서들과 충돌하면 구현 전에 사람에게 보고한다.

## 5. 작업 계획 보고

사람에게 아래 형식으로 보고하고, 명시적인 진행 승인을 받은 뒤 구현한다.

```text
이슈: #<번호> <제목>
브랜치: <브랜치명>
예정 PR 제목: type(scope): description (영어)
목적:
변경할 영역과 파일:
제외 범위:
완료 조건과 실행할 검사:
이슈에서 가져온 결정 사항:
확인이 필요한 사항: (없으면 "없음")
```

구현 중 이슈에 없는 결정이 필요해지면 멈추고 묻는다. 마무리는 `finish-task` 스킬로 한다.
