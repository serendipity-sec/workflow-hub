# 사용자에게 제공하는 검사 설명

`buildServiceReport(assessmentReport)`는 통합 정적 검사 결과를 검증한 뒤 한국어 설명으로 바꾼다. 새 검사를 수행하거나 원본 워크플로를 실행하지 않는다. LLM과 무관하게 동작하며, 프론트는 이 결과만으로 기본 설명을 표시할 수 있다. 계약 버전은 `serviceReportVersion: 1.0.0`이다.

## 화면에서 구분할 내용

| 필드                   | 표시할 내용                                        | 의미                                                                              |
| ---------------------- | -------------------------------------------------- | --------------------------------------------------------------------------------- |
| `executionStatus`      | 검사 완료 / 일부 도구 오류 / 검사 실패             | `completed`도 분석 범위 전체 확인이나 안전을 뜻하지 않는다.                       |
| `analysisStatus`       | 선언한 검사 범위 완료 / 추가 검토 필요 / 검사 실패 | 원본 결과와 대응한다. 원본의 `partial`·`unsupported`는 `review_required`다.       |
| `assessmentStatus`     | 원본 엔진 상태                                     | 기존 `partial`·`unsupported`·`error`를 그대로 보존한다.                           |
| `staticCoverageStatus` | 지원 범위 내 / 정적 분석 공백 있음 / 미평가        | 분석 공백이 없는 경우에도 환경 조건과 모델 범위가 남을 수 있다.                   |
| `functions`            | 어떤 기능으로 구성되어 있는지                      | 활성 노드의 알려진 기능 범주다. 업무 목적·실행 순서·실제 동작을 추측하지 않는다.  |
| `findings`             | 검토할 위험 후보와 설정·경로 근거                  | 심각도·claim을 보존한다. 정적 위험 후보를 확정된 실제 취약점으로 계산하지 않는다. |
| `observations`         | 확인한 기능·설정                                   | 원본 `info` 관찰이며 취약점 수나 수정 대상 수가 아니다.                           |
| `analysisGaps`         | 분석하지 못한 위치와 이유                          | 미지원 의미·처리 한도·정의 누락·도구 실패. 미등록 진단도 이 목록에 남긴다.        |
| `environmentChecks`    | 사용 전에 운영자가 확인할 조건                     | 실제 권한·목적지·입력 데이터·수신자·업무 정책 등의 근거 부재다.                   |
| `scopeNotes`           | 이번 검사의 지원 범위                              | 영어 중심 개인정보 모델, 정적 Python/AI 검사의 선언된 범위를 표시한다.            |

예를 들어 고객 문의가 AI로 전달되는 정의라면 외부 전송 위험 후보와 근거는 `findings`, 실제 AI 제공자의 데이터 보존·사용 허용 여부는 `environmentChecks`, 개인정보 모델의 언어 범위는 `scopeNotes`로 각각 표시한다. 해당 입력 흐름 자체를 해석하지 못했다면 `analysisGaps`도 남는다. 어느 목록도 숨겨서 전체 안전으로 표현하지 않는다.

각 카드는 `title`, `explanation`, `action`을 제공한다. `reference`의 `inputSha256`·`analysisKey`·`kind`·`id`로 정확한 원본 결과에 연결한다. 자식 파일의 finding은 자식 파일 해시를 사용하고, 누락된 자식 정의는 호출 부모의 위치를 사용한다. 구조 위치는 원본의 임의 필드 이름을 복사하지 않고 알려진 구조 키까지 축약한다. 노드 이름·메일 주소·SQL·Code·토큰·원문 값은 설명에 포함하지 않는다.

## 수정과 공개 판단

각 위험 후보의 `remediation`은 실제 검사 결과에 연결된 계획만 표시한다. 자동 수정도 원본 해시·지원 조건 확인과 새 파일 재검사가 필요하며, `behaviorPreserved: not_verified`를 유지한다. 관찰에는 자동 수정 버튼을 만들지 않는다. 지원 범위 밖 수정은 사람이 검토한다.

`decision`과 파일별 `policyDecision`·`publicationStatus`는 원본 정책 결과를 보존한다. `publication: requires_service_authorization`이며 이 설명 계층은 공개 보류를 승인으로 바꾸지 않는다. 사용자의 환경 확인과 서비스의 공개 검토 정책을 분리해 표시할 수 있지만 실제 승인·인가·공개 집행은 서비스가 담당한다.

## 한도와 LLM 보조

목록별 최대 256개 카드와 전체 직렬화 3 MiB 한도를 적용한다. 설명 팽창으로 바이트 한도에 가까워지면 관찰·범위 안내부터 생략하되, 각 목록의 전체 수와 생략 수를 유지한다. `counts`는 잘리기 전 전체 발생 수, `omitted`는 표시에서 생략한 수다. `truncated`가 참이면 원본 결과를 확인할 수 있는 안내를 함께 보여야 한다. 카드의 `omittedEvidence`와 `omittedRemediation`도 함께 표시한다. 각 수는 근거·관찰 발생 수이며 독립 취약점 수가 아니다. `vulnerabilityCount: not_established`를 유지한다.

LLM에는 원본 JSON 대신 고정 설명과 임시 근거 식별자를 전달할 수 있다. 모델은 먼저 읽을 근거 ID를 최대 8개 선택하고 워커가 원래 근거의 고정 설명을 작성한다. 모델의 자유 문장은 허용하지 않으며 원본 판정·분석 공백·생략 수를 변경할 수 없다. LLM 실패나 사용하지 않는 설정에서도 같은 기본 결과를 제공한다. 모델이 고른 항목은 전체 검사 결과와 구분한다.

## 검증

`test/service-report.test.mjs`는 상태 보존, 환경·언어 범위 분리, 도구 실패, 임의 문자열 비노출, 알려지지 않은 진단의 보수 처리, 수정 계획의 재검사 조건, 자식 해시 연결, 비활성 노드 제외, 총량 한도·생략 수와 상태 변조 거부를 검증한다. 이 테스트의 도구 출력은 단위용 모의 자료다. 실제 모델·도구 실행과 공개 JSON의 전체 검사는 별도 통합 검증 기록으로 구분한다.
