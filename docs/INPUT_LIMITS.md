# n8n JSON 입력 한도

최초 업로드(`POST /api/workflows`)와 버전 비교(`POST /api/workflows/{workflowId}/versions/{versionId}/comparisons`)는 같은 검증기(`N8nWorkflowValidator`)를 지난다. 파일 크기 5 MiB 상한 외에 아래 세 가지 규모 한도를 이 검증기에서 적용한다(#35).

> 상태: 구현됨. 한도 값은 실제 배포 환경이 아닌 합성 입력과 컨테이너(CPU·메모리 제한) 측정으로 정했고, 실제 n8n 파일로는 확인하지 않았다. 실제 사용자 워크플로와 실제 배포 서버에서의 확인은 [미검증 항목](#5-한계와-미검증-항목)에 있다.

## 1. 결정

| 한도      | 기본값 | 환경 변수                  | 초과 시                       |
| --------- | ------ | -------------------------- | ----------------------------- |
| 중첩 깊이 | 64     | `WORKFLOW_MAX_DEPTH`       | `422 WORKFLOW_LIMIT_EXCEEDED` |
| 노드 수   | 300    | `WORKFLOW_MAX_NODES`       | `422 WORKFLOW_LIMIT_EXCEEDED` |
| 연결 수   | 1,500  | `WORKFLOW_MAX_CONNECTIONS` | `422 WORKFLOW_LIMIT_EXCEEDED` |

- **측정 정의**: 깊이는 루트 객체를 1로 센 배열·객체 중첩 수, 노드 수는 `nodes` 배열 길이, 연결 수는 `connections` 아래 대상 항목(`{"node":...}`)의 총 개수다. 연결이 없는 `null` 출력은 세지 않는다.
- **경계**: 한도에 도달한 입력은 통과하고, 초과한 입력만 거절한다.
- **최소 깊이**: 연결이 하나라도 있는 워크플로는 구조상 문서 깊이가 6이다(루트 → `connections` → 소스 노드 → `main` 배열 → 출력 배열 → 대상 객체). 깊이 한도가 6보다 낮으면 연결이 있는 모든 파일이 거절되므로 6 미만의 값은 앱이 시작되지 않는다.
- **오류 응답**: `422`와 `WORKFLOW_LIMIT_EXCEEDED`. 메시지는 초과한 한도의 종류와 값만 알려 주며(예: `Workflow node count exceeds the limit (300)`) 파일 내용은 싣지 않는다. 구조 오류는 기존대로 `INVALID_WORKFLOW`이고, 413은 파일 크기 전용이다.
- **검사 순서**: 깊이(파싱 중), 노드 수, 연결 수 순서이며 처음 초과한 한도 하나를 보고한다. 깊이는 트리를 만들기 전에 파서가 끊는다.
- **저장된 기준 버전**: 비교 때 S3에서 읽은 기준 버전에도 같은 한도를 적용한다. 기준 버전이 넘으면 같은 코드이고 메시지가 `Base version: `으로 시작한다. 한도를 낮추기 전에 등록된 큰 버전은 한도를 올리기 전까지 비교할 수 없다.
- **거절된 요청의 부작용 없음**: 검증은 S3 쓰기와 정리 대상 기록, DB 쓰기보다 앞선다. 거절된 요청은 S3 원본·임시 객체, `pending_objects`, 버전·멱등성·비교 레코드를 만들지 않는다(API 테스트로 확인).
- **설정**: 환경 변수 값을 읽는 시점은 서버 시작이라 바꾸려면 재시작해야 한다. 노드·연결은 1 이상, 깊이는 6 이상이어야 하며 어기거나 숫자가 아니면 앱이 시작되지 않는다.

## 2. 왜 한도가 필요한가

5 MiB 상한은 바이트 수만 막고, 파싱한 뒤의 비용은 막지 못한다. 측정에서 확인한 것은 다음과 같다.

- **응답 크기 증폭**: 비교 응답은 기준·후보 두 그래프의 모든 노드와 연결을 담는다. 5 MiB 입력이 최대 31 MB 응답이 된다(연결 1개당 약 240 B, 노드 1개당 약 85 B).
- **동시 요청**: 요청 하나는 최악 입력에서도 1초 안쪽이지만, 동시 요청이 늘면 선형보다 나쁘게 느려진다. 힙 1 GB에서 최대 입력 비교 8개를 동시에 돌리면 31초가 걸리고 하나가 `OutOfMemoryError`를 냈다.
- **깊이**: 한도를 두기 전에도 Jackson의 기본 중첩 한도(문서 깊이 500)가 있었다. 우리가 정한 값이 아니었고 초과하면 원인을 알 수 없는 `File is not valid JSON`이 나왔다.

시간은 노드·연결 수에 선형으로 늘었다. 제곱으로 늘어나는 구간은 찾지 못했다.

## 3. 값을 정한 기준

- **허용 지연 기준(가정)**: 동시 비교 요청 10개의 첫 실행(서버 기동 직후)에서 가장 느린 요청이 5초 이내. CPU는 0.5코어, 힙 1 GB, 컨테이너 메모리 1.5 GB를 가정했다. 5초는 근거가 있는 수치가 아니라 팀의 판단이며, 바꾸면 한도도 바뀐다. 지연은 한도에 거의 비례한다.
- **서버 가정**: Lightsail 2 GB 인스턴스(2 vCPU, 2 GB RAM)를 가정했다. 지속 CPU는 문서에서 확인하지 못해 0.5코어를 보수적으로 가정했다.
- **하한(실제 파일): 확인하지 않았다.** 사용 예정인 실제 n8n 내보내기 파일로는 한도를 검증하지 않았으므로, 정상 파일이 이 한도에 거절되지 않는다는 것은 확인된 사실이 아니다. 이 값은 서버 보호 기준의 출발값이며, 이슈(#35)의 "실제 내보내기 파일 확인" 항목은 건너뛰기로 사람이 결정했다. 대신 공개 템플릿 340개를 표본으로 확인했으나(아래 4.6) 실제 파일을 대신하지 못한다. 실제 파일의 노드·연결·깊이를 확인하면 이 값과 4.5절의 지연 표를 같이 다시 보고, 걸리는 파일이 있으면 환경 변수로 올린다.

결과: **깊이 64 / 노드 300 / 연결 1,500**. 위 기준에서 가장 큰 후보이며, 측정에서 동시 10개 최대 지연이 4.5~4.8초였다. 여유는 약 4~10%로 얇다.

## 4. 측정 기록 (2026-11-23)

### 4.1 방법과 환경

- **대상**: 백엔드의 `N8nWorkflowValidator`와 `WorkflowGraphComparison`을 직접 호출했다(HTTP, Tomcat, S3, DB는 포함하지 않음). 입력은 모두 합성 JSON이며 기준 파일과 후보 파일은 같은 구조에서 파라미터 문자열만 다르게 했다.
- **측정값**: 요청의 wall 시간, 스레드 CPU 시간, 할당 바이트(`ThreadMXBean`), 직렬화한 응답 크기. 단일 요청은 워밍업 1회 뒤 3회의 중앙값, 동시 요청은 지정한 수의 스레드를 동시에 시작해 가장 느린 요청을 기록했다. "첫 실행"은 워밍업 없이, "워밍업 후"는 같은 입력으로 3회 비교한 뒤의 값이다.
- **무제한 측정**: 호스트 JDK(Temurin 25.0.2), `-Xmx1g`, 프로세서 2개.
- **제한 측정**: Docker 29.3.0(aarch64, VM CPU 8코어·메모리 4 GB)에서 `eclipse-temurin:25-jdk`(OpenJDK 25.0.5.1), `-Xmx1g`, `--memory=1500m`, `--cpus=0.5` 또는 `2`.
- **라이브러리**: Jackson 3.1.8(`tools.jackson`).
- **하네스**: 측정에 쓴 Java 소스(`Bench.java`)와 실행 스크립트는 저장소에 넣지 않았다. 입력 생성 규칙과 값은 아래에 적었다.

### 4.3 깊이 (한도를 두기 전의 동작)

문서 깊이 500까지는 통과하고 501부터 `422 INVALID_WORKFLOW "File is not valid JSON"`으로 거절됐다(Jackson 기본 한도). 깊이 1,000, 5,000, 20,000, 100,000 입력도 같은 오류로 거절됐고, 스택 오버플로(`-Xss512k`)는 재현하지 못했다. 한도 도입 뒤에는 깊이 65부터 `WORKFLOW_LIMIT_EXCEEDED`이며, 깊이 100,000 입력도 파싱 중에 거절하는 것을 테스트로 확인한다.

| 컨테이너 2코어           | 0.87 s |      - |  3.7 s |                               - |

0.5코어에서 워밍업 후 단일 요청은 0.77~0.83 s였다. 첫 요청이 느린 이유는 JIT 컴파일이 CPU 제한 안에서 요청과 경쟁하기 때문으로 보이며, 원인을 따로 분리해 확인하지는 않았다.

### 4.6 공개 n8n 템플릿 표본

실제 사용자 파일 대신 n8n의 공개 템플릿 API(`api.n8n.io/api/templates`)에서 340개를 받아 노드·연결·깊이를 셌다(전체 14,410개 중 인기순 상위 100개와 무작위 페이지 6개에서 페이지당 40개, 시드 35). 파일 내용은 저장소·로그에 남기지 않고 통계만 썼다.

|           |  중앙값 |     p90 |      p99 |     최대 |
| --------- | ------: | ------: | -------: | -------: |
| 노드 수   |      20 |      49 |       97 |      138 |
| 연결 수   |      14 |      41 |       79 |      138 |
| 중첩 깊이 |       8 |      11 |       11 |       11 |
| 파일 크기 | 14.7 KB | 44.7 KB | 121.7 KB | 158.6 KB |

채택한 한도(64 / 300 / 1,500)를 넘는 파일은 0개(0.0%)였고, 1,000 / 5,000 기준으로도 0개였다. 노드 한도 대비 최대 표본의 여유는 약 2.2배, 연결은 약 10배, 깊이는 약 6배다. 노드당 바이트 중앙값은 약 750 B로 합성 입력(330 B)의 2배 이상이어서, 파일 크기로 노드 수를 추정하기는 어렵다. 이 표본은 사용 예정인 실제 파일이 아니므로, 위 결과는 정상 파일이 한도에 거절되지 않는다는 보증이 아니라 참고 근거다.

## 5. 한계와 미검증 항목

- **실제 Lightsail 인스턴스에서 측정하지 않았다.** 지속 CPU를 모르고, 컨테이너는 Apple 실리콘(aarch64)에서 돌렸으며 배포 인스턴스의 CPU 아키텍처는 확인하지 않았다. 0.5코어는 가정이다.
- **HTTP 전체 경로는 측정하지 않았다.** Tomcat, 멀티파트 파싱, S3, DB, 프록시 지연이 빠져 있다. 업로드 검증은 비교보다 가벼워 최악으로 보지 않았으나 직접 측정하지는 않았다.
- **공개 템플릿은 운영 워크플로의 분포와 다를 수 있다.** 표본은 전체의 약 2.4%이고 공유용으로 다듬은 예제라 작은 쪽으로 치우쳤을 수 있다. 사용자 자신의 큰 워크플로가 한도에 걸리면 환경 변수로 올린다.
- **허용 지연 5초와 동시 10개는 가정이다.** 채택한 값의 여유가 4~10%라서 환경이 달라지면 기준을 넘을 수 있다.
- **동시 요청 수를 제한하는 장치는 없다.** 이 한도는 요청 하나의 비용을 줄일 뿐이며, 동시 요청이 더 많으면 지연이 늘어난다. 별도 결정이 필요하다.
- **깊이 초과는 예외 문구가 아니라 토큰으로 판별한다.** Jackson이 제약 종류를 구분하는 타입을 주지 않아, 파서가 제약에 걸려 실패했을 때만 깊이 제약을 푼 별도 파서로 토큰을 따라가며 깊이를 센다. 본 파싱과 같은 인코딩 자동 감지(UTF-8·UTF-16·UTF-32)를 쓰므로 인코딩과 무관하게 같은 결과가 나온다. 깊이 외의 제약(예: 이름 길이)은 기존대로 `INVALID_WORKFLOW`다. 입력 인코딩은 이전과 같이 Jackson의 자동 감지에 맡기며 UTF-8만 허용하도록 바꾸지는 않았다.
- **한도를 넘는 파일도 파싱까지는 비용을 치른다.** 깊이만 파서가 막고, 노드·연결 수는 트리를 만든 뒤 센다. 한도는 비교의 CPU·메모리와 응답 크기를 줄이기 위한 것이며 파싱 비용은 줄이지 못한다. 5 MiB 입력의 검증(파싱) 시간은 이번 측정에서 무제한 환경 최대 약 0.2초, 0.5코어 최대 약 0.7초였고(단일 측정, 잡음 포함) 동시 업로드가 몰리는 경우는 측정하지 않았다.
- **저장된 기준 버전이 한도를 넘으면 클라이언트가 고칠 수 없다.** 수정본을 고쳐도 `422`가 반복되고, 운영자가 한도를 올리고 재시작해야 풀린다. 새 버전 등록은 비교가 먼저라 그 워크플로의 등록도 막힌다. 기준 버전에도 같은 한도를 적용하기로 한 결정의 대가이며 운영 데이터가 없는 지금은 영향이 없다. 운영 데이터가 생긴 뒤에 한도를 낮추려면 기준 버전이 걸리는지 먼저 확인한다.
- **등록은 저장된 비교 파일을 다시 검증하지 않는다.** 비교 뒤 24시간 안에 한도를 낮추고 재시작하면 새 한도를 넘는 버전이 만들어질 수 있고, 그 버전의 이후 비교는 위 `Base version:` 오류가 난다. 이슈(#35) 범위가 최초 업로드와 비교라서 등록에는 적용하지 않았다.

## 6. 값을 바꿀 때

한도는 지연에 거의 비례한다. 올리려면 4.5절의 표를 참고해 허용 지연 기준과 서버 사양을 같이 본다.

- 정상 파일이 `WORKFLOW_LIMIT_EXCEEDED`로 거절되면 해당 환경 변수를 올리고 재시작한다. 거절 메시지에 초과한 한도와 값이 있다.
- 서버 사양(CPU)을 늘렸다면 같은 지연 기준에서 더 큰 한도를 쓸 수 있다.
- 값을 바꾼 뒤에는 한도 크기의 합성 파일로 비교 요청을 동시에 여러 개 보내 지연을 다시 잰다. 입력은 이 문서의 4.2절 규칙(노드 `{"name","type","parameters"}` 형태, 연결은 앞 노드로 순환하는 대상 항목)으로 만들 수 있다.
