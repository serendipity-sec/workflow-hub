# Bounded static AI connection and data contracts

`src/ai-flow.ts` provides three rules at profile `1.2.0`:

- `N8N_AI_CONNECTION_CONTRACTS` (`dependencies`) records reviewed node definitions, typed connection compatibility, tool capabilities, required inputs and approval declarations.
- `N8N_AI_PROMPT_DATA` (`egress`) records possible prompt/context transfers to attached models, retaining public components, declared internal components, secret candidates, personal-data candidates and unknown components together.
- `N8N_AI_VECTOR_DATA` (`egress`) records possible document/query transfers to embedding providers and vector stores. [Vector data and binary provenance](ai-vector-binary.md) describes the added exact profiles, input selection and strict binary-absence conditions.

The rules receive the normalized `Context`, the shared `ValueFlow` and optional validated operator evidence. They do not invoke models, tools, credentials, network services, Code nodes or uploaded expressions. A declared connection is not an observed invocation; a format schema is not a sanitizer; a schema-valid model argument is not authorization.

## Data and authority boundaries

The edge helpers accept only reviewed producer/consumer roles, output index zero and enabled definitions. The main model uses input zero; an explicitly enabled fallback on a reviewed Agent V2/AgentTool/LLM chain uses input one. Each model slot accepts one definition. Memory, parser and retriever inputs also enforce their one-connection limit; tool inputs can accept multiple tools. The runtime model's compatibility and exact selection remain unresolved. These slots and cardinalities are checked against the fixed [input-connection validator](https://github.com/n8n-io/n8n/blob/86dff76e10efba250a4d3e57760e4eb5d2bbea25/packages/core/src/execution-engine/node-execution-context/utils/get-input-connection-data.ts). Wrong ports, dynamic mode selectors, disabled or unknown definitions do not become covered routes. Connections contain raw node names internally, but reports use hashed identities and structural locations on the two endpoints.

`aiPromptInputs(node, context?)` exports selected inputs for the value-flow layer on main-output Agent/LLM/retrieval chains. Supplying context enables bounded binary provenance; internally generated source entries carry their producing node's evaluation context. A literal prompt does not inherit unrelated upstream item data. A dynamic or malformed selector contributes unknown, not a guessed literal prompt. Unknown runtime context is represented explicitly: the helper's `value: undefined` entries are placeholders for unavailable contents, not public JavaScript literals or expression-parser failures. Callers must retain an unknown AI result even when all selected text is public. No output projection may use a structured parser to discard the input's secret/PII candidates or inherit a guard.

External prompt influence on attached tools is reported as a candidate, with the original data-source location and tool definitions. Tool responses, memory histories, retrieved documents and runtime binary attachments add unknown context. Manual schema descriptions and selected literal prompt components can still add personal-data candidates; unknown does not erase them. Subnode item binding is unresolved, so a `$fromAI` placeholder never implies a public, sanitized or authorized argument. Automatic tool descriptions and inactive parser examples do not create transfers of unused literal fields. Active JSON examples are converted into schemas by [schemaParsing](https://github.com/n8n-io/n8n/blob/86dff76e10efba250a4d3e57760e4eb5d2bbea25/packages/@n8n/nodes-langchain/utils/schemaParsing.ts); the worker retains unknown generated schema content instead of claiming literal example values were sent.

Nested AgentTool, retrieval-tool and parser auto-fix models are evaluated separately. Potential model-generated arguments/retry outputs retain initiating prompt candidates and unknown contents. This is a conservative dependency, not proof that a particular secret was generated or sent. Memory constant custom session keys are a possible isolation concern only; the rule does not claim a demonstrated cross-user leak.

Native ToolCode and [Workflow V1](https://github.com/n8n-io/n8n/blob/86dff76e10efba250a4d3e57760e4eb5d2bbea25/packages/@n8n/nodes-langchain/nodes/tools/ToolWorkflow/v1/ToolWorkflowV1.node.ts) include `inputSchema` only when `specifyInputSchema` is active and `schemaType` is manual. The default `fromJson` path keeps generated-schema uncertainty without treating literal example values as model input. Unknown enablement/selectors keep possible active inputs and unknown. Code bodies, inactive examples, embedded workflow definitions and unrelated parameter strings are not model schema metadata merely because they contain `$fromAI`. Native HTTP placeholder schema conversion and provider serialization are not fully modeled; context/results remain unknown.

Each attached OpenAI model's request data includes `extraBody` in either API mode and, when Responses is active, metadata, safety/cache/conversation identifiers, prompt variables, selected JSON text schemas and built-in search settings. Unresolved selectors/options preserve unknown. Nested supplied objects are inspected with a finite budget, and evidence never exposes arbitrary field names. Built-in search/code capabilities retain unknown remote results and unverified permissions. Request data is evaluated as common Agent context plus that model's own configuration; a primary model's metadata is not assigned to its fallback model's transfer policy. OpenRouter's explicit freeform routing lists are included; credentials, local retry/timeout settings, static model identifiers and numeric generation controls are not prompt content. Runtime request construction and option validation remain unverified.

Only the fields parsed as JSON by the pinned source (`metadata`, prompt variables, text schemas, file-search IDs/filters and `extraBody`) receive bounded data-JSON parsing. Their object keys retain field-name sensitivity hints. String values inside parsed JSON are literal data, including text that resembles `={{ ... }}`; they are never parsed again as n8n expressions. Ordinary identifiers and location/domain strings receive no JSON interpretation. Invalid, dynamic or truncated JSON retains a separate unknown remainder. The shared parser caps input at 65,536 characters, depth 16, 2,048 visits and 512 members per object.

`ai_model` destination policy is scoped to the model node key. A reviewed OpenAI model's explicit static `options.baseURL` and the reviewed Groq provider's fixed API origin can provide known configured origins. Credential-selected OpenAI, Gemini and OpenRouter hosts stay unresolved. URL userinfo, dynamic endpoints and incompatible model routes cannot satisfy an endpoint allowlist. AI and connector transfers share `transferDataClasses`: classifications bind the normalized node key and source selection, including `internal`. The separate `ai_prompt_to_model_internal_component` finding retains that declared class rather than relabeling it unknown. Explicit whole-document and unresolved-collection dependencies also preserve matching descendant candidates with an unknown remainder; unrelated nodes, sibling fields and unmatched paths do not supply classifications. Partially classified joins and unresolved transformations retain unknown alongside known classes. Conflicting classifications for one exact origin are rejected when parsing the sidecar. Mixed known internal/secret/PII classes still cause a policy denial when disallowed, even if other components or the endpoint are unknown. A policy can allow fully classified data at the declared endpoint while model invocation and output remain unverified; allowing unknown in a policy never resolves unknown context or proves an actual model call.

Operator `aiApprovals` must bind both the consuming agent and tool node. A declaration that approval is required leaves runtime enforcement unresolved. Prompt text, tool descriptions, output schemas and workflow node names cannot supply approval authority. Credential permissions, tool destination validation, database privileges, referenced workflow access, model attack resistance and actual tool selection remain conditions for an operational review.

## Limits, masking and validation

The worker's existing workflow limits remain in force. AI inspection additionally limits context recursion to 8 levels, chat messages to 32, inspected tool-parameter values to 512, each inspected string to 65,536 characters, and retained `$fromAI` declarations to 32. Model request settings use at most 128 visited values and depth 8. Each rule retains at most 64 findings and 64 ordinary diagnostics plus one explicit result-limit diagnostic. Finding evidence retains at most 20 locations; truncation is diagnosed. Cycles, malformed shapes and limits preserve partial/unsupported coverage.

Reports never reproduce prompt text, model names, tool descriptions, endpoint URLs, SQL/Code, session keys, custom parameter names or raw origin field paths. They contain fixed codes, node hashes and fixed structural locations only. Findings are configuration facts or possible transfers, never a claim that an AI tool invocation was observed.

`test/ai-flow.test.mjs` uses synthetic definitions to exercise mixed sensitivity, literal independence, auto/guardrails selection, malformed selectors/options, binary uncertainty, tool-selection candidates, typed-port mismatch, fallback multiplicity, unsupported versions, parser non-sanitization and retry models, memory/retrieval context, HTTP/SQL/Code/workflow tools, `$fromAI` metadata, exact approval scope, endpoint/data-class policy, exact internal declarations, partial and multi-origin classification, conflicting source declarations, disabled definitions, cycles, budgets, masking and deterministic output. A Code sentinel verifies that stored code is never executed by these checks. The frozen public corpus is static input only; new static findings are not live exploit, model or API evidence.

On 2026-11-23, the initial local read-only pass of all 15 frozen workflow files, before independent-review fixes to tool/model request metadata, produced schema-valid results for these two rules: 19 reviewed node definitions, 7 covered typed edges and 45 findings. These historical counts describe that rule-pair pass, not current whole-worker completion. Templates 7622 and 7643 store their model/parser edges in the reverse direction (Agent to Model/Parser). The worker preserves those original edges and reports missing required inputs and unresolved contracts; it does not silently invert the graph. Frozen 0.5 reports were preserved. Their broad diagnostic occurrences were `ai_node_semantics_unreviewed` 21, `non_main_connection_semantics_unreviewed` 9 and `partial_workflow_topology` 24. These old counts are not a before/after safety score.

The existing broad diagnostics are not simply removed. A caller may use `isReviewedAiNode` and `coveredAiEdge` to replace a generic AI-definition warning with this narrower contract plus runtime limitations. Main-flow-only rules still have their own `partial_workflow_topology` limitation. Completing these static contracts does not complete team API integration or prove production authorization controls.
