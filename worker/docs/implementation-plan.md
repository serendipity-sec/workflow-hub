# #14 보안 워커 구현 설계와 작업 분할

이 문서는 첫 기본 규칙 구현의 기준을 보존한다. 후속 확장과 현재 기본 진입점은 [통합 assess 명세](assessment.md), [SEC 25개 대응표](assessment-evidence.md), [값 흐름](value-flow.md), [의미 비교·수정](assessment-change.md)에 구현·검증 기준을 추가했다. 아래의 초기 미지원 항목은 현재 지원표와 함께 확인한다.

2026-11-22 사용자 결정에 따른 실행 설계다. 대상은 `worker/`의 10개 정적 검사다. 기존 `feat/14-integrate-security-worker` 브랜치에서 검증한 단위로 커밋하고 PR 생성·타인 승인·선행 PR 머지를 개발 조건으로 두지 않는다. 프론트·백엔드 구현이 끝난 뒤 실제 API에 워커를 맞추는 일은 #18이며 이번 구현에 포함하지 않는다.

## 설계 문서의 상세도와 보완점

[SECURITY_DESIGN](../../docs/SECURITY_DESIGN.md)은 검사 유형, 신뢰 경계, 데이터 흐름/방어 조건, 근거·재검사와 평가 원칙을 설명한다. [DIFFERENTIATION](../../docs/DIFFERENTIATION.md)은 기존 도구와 비교할 이유·자료·검증 기준을 제공한다. 두 문서는 규칙별 필드/버전 지원표, 실행 가능한 결과 스키마, 오류 처리와 코드 소유권까지 정한 구현 명세는 아니었다.

이번 구현은 다음 공백을 채운다.

- 기존 단일 SQL 결과와 별도로 10개 카테고리를 항상 포함하는 `2.0.0` 정적 보고서.
- 입력을 실행하지 않는 공통 JSON/그래프 문맥과 원문을 출력하지 않는 위치 표현.
- 규칙·대상 위치별 `checked`, `partial`, `unsupported`, `not_applicable` 범위.
- 오픈소스의 채택·미채택 이유, 고정 버전·라이선스·실제 실행 증거.
- 규칙 모듈을 빠뜨리면 전체 결과 스키마 검증이 실패하는 통합 지점.
- 입력 오류·도구 실패·제한 초과를 깨끗한 결과로 바꾸지 않는 실행기.
- 정상·위험·미지원 및 공개 정의 호환성을 구분하는 검증 기록.

## 처리 순서

1. 원본 바이트를 제한해 읽고 SHA-256을 계산한다. UTF-8·JSON 중복 키·깊이·노드/연결 한도를 검증한다.
2. 노드·연결·분기·원본 필드를 유지하는 내부 문맥을 만든다. 원본 문자열과 사용자 지정 키는 내부에서만 사용한다.
3. 신뢰된 컨트롤러가 고정 Gitleaks 실행 파일에 문자열 필드를 stdin으로 전달한다. 원문은 임시 파일에 저장하지 않는다. 버전·시간·출력·종료·정리를 확인한다.
4. 권한을 제한한 Node 자식 프로세스에 원본과 정제한 도구 결과를 전달한다. 분석기는 네트워크 요청, 표현식 평가, 워크플로 실행, 사용자 패키지 설치를 하지 않는다.
5. 내용 검사 2개, 설정/코드 검사 4개, 흐름 검사 4개를 합친다. 한 규칙의 미지원이 다른 규칙의 확인된 근거를 지우지 않는다.
6. 모든 카테고리, 참조 관계, 파일 해시, 결과 크기를 검증한 뒤 JSON 보고서를 반환한다. 실제 값·노드 이름·주소·토큰을 결과에 복사하지 않는다.
7. 같은 보고서 계약의 수정 전후 관측을 비교한다. 경고 소실을 일반적인 수정 성공으로 표시하지 않는다.

새 로컬 진입점은 `node dist/cli.js scan <workflow.json>`이다. `WORKER_GITLEAKS_PATH`는 실행 환경 관리자가 지정하는 절대 경로이며 업로드 파일에서 읽지 않는다. 도구가 없으면 비밀정보 검사의 누락을 보고서에 남긴다. 기존 `local`/`mock-once`와 `1.0.0` SQL 계약·저장된 근거는 호환 경로로 보존한다. 새 계약은 실제 팀 HTTP API를 확정하지 않는다.

## 10개 항목의 구현 분할

아래의 지원은 정적 프로파일 범위다. 실행 가능한 모든 n8n 노드나 개인정보 유형을 지원한다는 의미가 아니다. 정밀 노드 버전·필드는 각 모듈의 프로파일과 [흐름 지원표](flow-profiles.md), [설정·코드 지원표](settings-profiles.md), [도구 선택 근거](oss-decisions.md)에 기록한다.

| 항목                 | 구현과 재사용                                                                | 결과의 의미와 한계                                                                               |
| -------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 1. 비밀정보          | Gitleaks 8.30.1 + 설정/헤더의 직접 입력 값 후보, 키·메모·pinData 포함        | 비밀정보 후보이며 키 유효성을 외부에 확인하지 않음. 도구 누락/실패는 부분 검사                   |
| 2. 개인정보          | validator.js의 이메일·결제카드 형식/검사값·한국 휴대전화 검증                | 선언한 세 유형의 후보. 실제 인물 여부, 이름/주소/한국 개인정보 전반의 NER은 지원하지 않음        |
| 3. 요청자 검증       | Webhook 인증 설정과 선언된 credential 참조                                   | 설정 상태만 확인. 프록시 인증·실제 권한 집행은 미확인                                            |
| 4. 외부 전송         | 지원 HTTP/전송 필드와 입력 참조 경로                                         | 전송 지점/데이터 경로이며 실제 유출 또는 목적지 악의를 확정하지 않음                             |
| 5. SSRF              | HTTP URL의 고정 origin과 동적 목적지 구분, 지원 입력 경로                    | 실제 DNS·리다이렉트·내부망 접근은 실행하지 않음                                                  |
| 6. SQL               | Postgres 단순 SELECT의 보간/바인딩/엄격 숫자 guard, 추가 형식의 한계         | 과거 규칙의 정확한 바인딩 근거 유지. 일반 SQL·동적 식별자를 안전 판정하지 않음                   |
| 7. 명령/코드         | ExecuteCommand 입력, acorn으로 Code JavaScript AST 정적 구조 읽기            | 고권한 기능·후보 호출의 근거. 코드를 실행하지 않으며 임의 프로그램의 완전한 흐름을 해석하지 않음 |
| 8. 통신              | 지원 HTTP 설정의 평문/인증서 검증 비활성화/URL 인증정보                      | 설정 근거이며 실제 TLS·프록시·외부 라이브러리 동작은 미확인                                      |
| 9. 응답/로그         | RespondToWebhook/응답 설정의 전체 입력 전달과 Code AST의 제한된 console 호출 | 노출 범위의 설정/경로. 데이터가 실제 개인정보인지는 별도 정보가 필요                             |
| 10. 외부 의존/고권한 | 커뮤니티·SSH·파일·하위 워크플로·AI 도구 연결 식별                            | capability/누락 의존성 표시. typeVersion을 npm 버전으로 치환하거나 CVE 검사 완료로 표시하지 않음 |

## 작업별 소유권과 통합 순서

| 작업              | 담당 경계                                       | 완료 확인                                                     |
| ----------------- | ----------------------------------------------- | ------------------------------------------------------------- |
| S0 공통 계약·문맥 | static-contract/context, 해당 테스트            | 모든 10개 카테고리, 근거/범위 참조 검증, 원문 누출 방지       |
| S1 내용 검사      | static-content/gitleaks, 내용 테스트, 도구 증거 | 정상·후보·누락/실패·강제 제외 주석·환경 설정 간섭             |
| S2 설정·코드      | static-settings, 설정 테스트                    | 버전별 설정/기본값, Code AST 성공/실패, 고권한·미확인         |
| S3 흐름           | static-flow, 흐름 테스트                        | 현재/직접 참조, 무관한 IF, 변환/합류/순환의 한계              |
| S4 실행·통합      | static-engine/analyzer/runner/cli, 통합 테스트  | 해시·취소·시간·출력·모든 카테고리·오류·도구 누락              |
| S5 비교           | static-compare, 비교 테스트                     | 지속/새 관측/미관측/불확실, 노드 삭제·규칙 변경               |
| S6 실측·문서      | 검증 하네스와 보고서, README/지원표             | 기존 회귀, 실제 Gitleaks, 공개 원본 정적 검사, 전체 결과 대조 |

공통 파일은 한 담당자만 편집한다. 오케스트레이터가 계약과 통합을 책임지고, 다른 담당자는 배정한 모듈·테스트만 변경한다. 각 담당자는 구현한 프로파일·실행 명령·실패·미지원과 남은 문제를 반환한다. 메시지로 완료를 받았다는 이유만으로 완료 처리하지 않고 실제 코드와 테스트 결과를 확인한다.

## 작업이 멈추거나 목적이 바뀌지 않도록 하는 규칙

- 일상적인 구현·테스트 실패는 담당자가 수정하고 다시 검증한다. 같은 실패를 반복하면 원인 분석을 독립 담당자에게 넘긴다.
- 외부 라이브러리 부재는 먼저 실제 설치/라이선스/실행 가능성을 확인한다. 미사용을 숨기거나 가짜 도구 결과를 만들지 않는다.
- 실제 API·계정·운영 격리 정보의 부재는 #18의 후속 조건이다. 독립 정적 검사 구현을 중단하는 이유로 쓰지 않는다.
- 새 위험 유형을 추가할 때 기존 양성·정상·미지원 회귀를 유지한다. 테스트 삭제·skip으로 통과시키지 않는다.
- 검사는 읽기 전용 정적 분석이다. 공격 성공 재현·사용자 워크플로 실행·실제 서비스 요청을 추가하지 않는다.
- 커밋은 변경한 단위의 검사와 자체 점검 후 생성한다. 여러 담당자가 같은 브랜치를 수정하므로 선택한 파일만 커밋한다.
- 날짜 목표와 검증된 완료를 구분한다. 보고서에는 구현 항목, 실제 지원 범위, 도구/프로파일 버전, 통과/실패/미지원과 외부 조건을 남긴다.

## 검증 기준과 확장 경계

기존 51개 회귀와 고정 합성 12개의 저장 근거를 보존한다. 새 검증에서는 10개 카테고리의 양성·음성·미지원 사례, 원문 마스킹, 해시·출력 한도, 도구 실패, 경고 소실 반례를 포함한다. 공개 파일은 내려받은 원본을 실행하지 않고 정적 검사하며 원본 바이트 해시·출처·실제 결과를 기록한다. 공개 파일 전체를 지원한다고 가정하지 않는다.

실행 환경 연계는 확장 경계다. 실제 설치 패키지 버전·권한·네트워크 정보를 받기 전에는 미확인으로 표시한다. 운영 OS 격리, 실제 API, 개인정보 유형 확대, 임의 코드/복잡한 Merge/재귀 하위 워크플로의 정밀 해석, 자동 수정과 동적 AI 평가는 구현·검증되지 않은 상태를 명시한다.
