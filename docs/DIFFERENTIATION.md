# 기존 기능 비교와 차별화 검증 계획

확인일은 2026년 11월 21일이다. 비교 범위는 아래 공개 자료에 기술된 기능이다. Workflow Hub의 기능과 평가 방법은 팀 검토용 제안이다.

## 1. 현재 결론

n8n은 인스턴스 감사, 공식 템플릿 검토, 특정 버전의 게시 승인 절차를 제공한다. FlowGuard와 n8ncheck는 이미 JSON 구조와 노드 관계를 검사한다. AIronClaw의 MCP 보안 제품은 발견 항목의 근거와 조치 안내, 정책 적용 후 재검증을 연결한다. [n8n 보안 감사](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/run-security-audits.md), [n8n 템플릿 제출과 검토](https://support.n8n.io/article/becoming-an-n8n-template-creator-and-getting-help), [n8n 워크플로 검토](https://docs.n8n.io/build/manage-workflows/workflow-reviews), [FlowGuard](https://github.com/MohibShaikh/FlowGuard#readme), [n8ncheck](https://github.com/mewuto/n8ncheck#readme), [AIronClaw 보안 검사와 조치 확인](https://blog.aironclaw.com/mcp-security-scan-toolkit/)

Workflow Hub에서 검증할 사용자 과제는 **다른 사람이 만든 n8n 파일을 내 계정과 데이터에 연결하기 전에 위험을 이해하고, 수정한 파일을 다시 검사해 사용할 버전을 고르는 것**이다. 같은 리비전의 파일·검사·정책 결과를 연결하고, 업데이트를 검토할 때 새 목적지·권한·위험 경로와 미확인 항목을 보여주는 흐름을 제안한다. 비교 우위는 6절의 가설을 구현과 평가로 검증한 뒤에 주장할 수 있다. [개발 계획](PLAN.md), [보안 설계](SECURITY_DESIGN.md)

## 3. 위험이 있는 파일이 계속 공유될 수 있는 이유

아래는 공개 자료에서 확인한 동작을 바탕으로 도출한 가능성이다. 실제 발생 빈도는 따로 측정해야 한다.

- **공유 경로별 검토 범위.** n8n JSON을 직접 공유하거나 GitHub에 올린 파일도 가져올 수 있다. 공식 템플릿 심사와 독립된 유통 경로가 있으면 도입하는 사람이 출처와 검토 이력을 확인해야 한다. [n8n 템플릿 제출](https://support.n8n.io/article/becoming-an-n8n-template-creator-and-getting-help), [JSON 가져오기](https://docs.n8n.io/build/manage-workflows/export-and-import.md)
- **가져오는 환경의 차이.** 연결 계정의 권한, 앞단 인증, 하위 워크플로, 네트워크 정책에 따라 같은 JSON의 접근 범위와 영향이 달라질 수 있다. 자격 증명 참조 이름이나 직접 입력한 헤더 등은 파일에 남을 수 있다. [n8n 검토 범위](https://docs.n8n.io/build/manage-workflows/workflow-reviews), [공유할 때 자격 증명 처리](https://docs.n8n.io/build/manage-workflows/export-and-import.md)
- **동적 구성과 미지원 경로.** 동적 목적지, 임의 코드, 커뮤니티 노드 내부 동작, 확인할 수 없는 하위 워크플로 때문에 파일에서 정적으로 판단할 범위가 제한된다. 방어 조건과 사용 환경을 확인할 수 있는 범위를 결과에 표시한다. [보안 설계의 지원 범위와 데이터 흐름](SECURITY_DESIGN.md)
- **수정 후 달라지는 위험.** 목적지·권한·입력 경로가 바뀔 때 이전 판단의 근거도 다시 확인해야 한다. 최신 저장본을 가리키는 링크를 통해 받은 파일은 이전에 검토한 파일과 달라질 수 있다. [Make Scenario sharing](https://help.make.com/scenario-sharing), [n8n 버전 고정 리뷰](https://docs.n8n.io/build/manage-workflows/workflow-reviews)

## 4. 공개 템플릿 조사 결과의 해석

AIronClaw는 n8n.io의 조회수 상위 1,000개와 GitHub 커뮤니티 저장소의 파일을 포함해 12,750개 템플릿을 정적으로 검사했다고 보고했다. 보고서의 34,880개는 탐지 항목의 수다. 인증 전에 도달 가능하다고 분류한 716개 워크플로도 도구의 판정에 근거하며, 별도로 고른 6개 사례는 지정 환경에서의 실행 결과를 보고한다. 표본 선정, 중복 제거, 규칙 범위, 사용 환경을 고려해 해당 조사 범위의 관측으로 읽는다. 이 수치로 전체 생태계의 취약률, 운영 중 악용 빈도, 제품 수요를 추정하려면 추가 자료가 필요하다. [AIronClaw 조사 방법과 결과](https://blog.aironclaw.com/n8n-12k-templates-critical-vulnerabilities/)

Workflow Hub에서는 자체 평가 사례의 정답 라벨과 검사 범위를 먼저 정한다. 정적 설정·위험 흐름의 탐지, 합성 환경에서 확인한 방어·정상 동작, 분석에 필요한 추가 정보를 각각 기록한다. [보안 검사 검증 계획](SECURITY_DESIGN.md)

## 5. 개선을 검토할 구체적인 사례

- **값과 방어 조건.** IF가 검증한 필드와 실제 작업에 사용되는 필드의 일치 여부, 관련 분기 전체에 검증이 적용되는지, 이후 값이 다시 바뀌는지 비교한다. SQL 쿼리의 값 바인딩도 지원하는 노드·버전에서 실제 쿼리와 매개변수의 관계를 확인한다. 기준 도구와 같은 정상·위험·분석 불가 사례로 평가한다. [방어 조건과 유형별 판정](SECURITY_DESIGN.md)
- **업데이트 준비.** 새 외부 전송, 인증 설정 변경, 쓰기 권한 추가, 분석 범위 감소를 검토자가 찾을 수 있는지 확인한다. 가능한 경우 두 리비전을 동일한 규칙으로 검사하며, 규칙 차이와 파일 변경에 따른 결과를 기록한다. [리비전별 보안 변화](SECURITY_DESIGN.md)
- **수정본 사용.** 수정 효과와 정상 업무 동작을 합성 사례에서 확인한다. 검사한 리비전에서만 해당 근거를 제공하고, 배포 파일이 정제되어 바뀌면 새 리비전 검사를 연결한다. [수정·재검사·공개 구조](ARCHITECTURE.md)

## 7. 비교와 사용자 검증

1. **공통 사례를 준비한다.** [보안 설계의 합성 사례](SECURITY_DESIGN.md)를 바탕으로 위험 설정, 정상 설정, 노드·버전 미지원, 입력 정보 부족, 리비전 변경 사례를 준비한다. 기대하는 노드·필드·상태를 검사 결과를 보기 전에 기록한다.
2. **분석 효과를 비교한다.** 도구의 버전·규칙·설정과 사례 ID·해시를 기록한다. 같은 원인에 대한 중복 경고의 집계 기준과 판정 단위를 고정한다. 공통 지원 사례의 정밀도·재현율과 전체 사례의 분석 범위를 함께 보고한다. 미지원과 오류의 분모를 명시한다.
3. **화면과 설명 효과를 비교한다.** 같은 검사 결과를 사용한 과제로 표현 방식의 영향을 측정한다. 검토 순서를 참가자 사이에서 바꾸고, 동일한 질문과 채점 기준을 적용한다. 과제·참가자 수와 측정 조건을 함께 밝힌다.
4. **수정과 파일 일치를 검증한다.** 같은 규칙으로 양쪽 리비전을 검사하고, 정상 동작과 방어 조건을 확인한다. 선택한 리비전의 해시와 다운로드 바이트를 대조한다. 공개 정책이 구현되면 정책 기록의 대상과 파일도 대조한다.
5. **측정한 범위에서 결과를 설명한다.** 표본 구성, 비교 가능한 범위, 예외, 원시 측정값을 남긴다. 기존 도구 출력을 설명해 얻은 사용자 효과와 자체 분석에서 추가로 확인한 정탐을 각각 보고한다.

첫 통합 검증에서는 합성 워크플로의 업로드부터 근거 확인, 수정본 생성, 재검사, 리비전 비교까지 수행한다. 공개 정책이 채택되면 선택한 리비전의 공개와 다운로드 일치까지 포함한다. [개발 단계와 완료 조건](PLAN.md)
