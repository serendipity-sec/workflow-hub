# 보안 검사 설계안

> 팀 검토용 제안 · 2026-11-21

이 문서는 Workflow Hub에 추가할 워크플로 보안 검사의 범위와 판정 근거를 제안한다. 현재 배포된 기능, 확정된 API 계약, 실행된 DB 스키마를 나타내지 않는다. 팀이 채택한 내용은 관련 이슈에 결정과 이유를 기록하고 문서의 상태를 갱신한다.

제품 범위와 개발 순서는 [PLAN.md](PLAN.md), 시스템 구성과 데이터·권한 경계는 [ARCHITECTURE.md](ARCHITECTURE.md), 실제 구현된 HTTP API는 [OpenAPI](../contracts/openapi.yaml)를 기준으로 한다. 이 문서는 검사 방법, 결과의 의미, 검증 기준을 관리한다. 비교 대상과 제품 효과의 평가 방법은 [DIFFERENTIATION.md](DIFFERENTIATION.md)에서 다룬다.

## 1. 목적과 유지할 원칙

### 사용자에게 제공할 판단

외부 n8n 워크플로를 자신의 계정·데이터에 연결하려는 사용자가 다음을 판단할 수 있게 한다.

1. 누가 워크플로를 실행할 수 있으며, 어떤 입력이 중요한 작업에 영향을 주는가?
2. 어떤 데이터를 읽고 어디로 보내며, 어떤 권한과 위험 작업을 요구하는가?
3. 파일에서 확인한 사실, 추가로 필요한 사용 조건, 현재 분석하지 못한 부분은 무엇인가?
4. 이전 리비전과 비교해 무엇이 위험해졌고, 수정으로 어떤 문제가 해소됐는가?
5. 공개·다운로드하는 파일은 어떤 검사와 정책 평가를 거친 정확한 버전인가?

검사 결과는 사용자가 조치할 수 있는 근거를 제공한다. 모든 실행 환경에 대한 안전 보증이나 인증으로 표현하지 않는다.

### 기존 원칙과 추가할 검사 경계

- 업로드한 워크플로, Code 노드, 표현식은 일반 서비스와 정적 분석 워커에서 실행하지 않는다.
- 외부 시스템에 접속해 업로드된 키의 유효성을 시험하거나, 발견한 URL로 자동 요청하지 않는다.
- 실제 자격 증명·개인정보·고객 워크플로를 테스트 샘플이나 로그에 넣지 않는다.
- 사용자별 서비스 데이터 접근은 백엔드를 경유한다. 파일·검사·수정안·공개 작업은 대상 리비전의 권한을 확인한다.
- 현재 저장소의 기술 스택과 별도 보안 워커 방향을 유지한다. 상세 배치와 작업 처리 방식은 아키텍처 문서와 구현 이슈에서 정한다.

### 결과에 사용하는 용어

| 구분             | 의미                                                      | 허용되는 설명                                                      |
| ---------------- | --------------------------------------------------------- | ------------------------------------------------------------------ |
| 설정 확인        | 파일에 존재하는 값이나 기능을 확인                        | 인증서 검증을 끄는 설정이 있음                                     |
| 위험 가능성      | 위험 패턴과 필요한 전제 중 일부를 확인                    | 외부 입력이 요청 URL에 사용되지만 호스트 제한 여부는 분석하지 못함 |
| 위험 경로 확인   | 지원 범위에서 입력 출처·전달 경로·위험 작업의 연결을 확인 | 요청 본문 값이 지원하는 DB 노드의 SQL 문자열에 직접 삽입됨         |
| 통제된 실행 검증 | 합성 사례의 방어·정상 동작을 지정한 테스트 환경에서 확인  | 지원 사례에서 수정 후 제한이 적용되고 정상 업무가 유지됨           |
| 미확인           | 파일에 정보가 없거나 분석이 지원되지 않음                 | 앞단 인증·실제 DB 권한·미제공 하위 워크플로는 확인하지 못함        |

실행 검증 근거는 테스트한 파일 해시와 환경에 한정한다.

## 2. 위협 모델

### 보호 대상

- 사용자의 비공개 워크플로, 원본·수정본과 수정 계보
- 파일에 포함될 수 있는 비밀정보, 개인정보, 내부 주소와 업무 데이터
- 검사 결과·수정안·정책 평가의 정확한 대상과 변경 이력
- 서비스 로그인 토큰, DB·S3·워커의 자격 증명
- 검사 서버의 자원과 외부 네트워크 접근 권한
- 사용자가 실제로 내려받는 파일과 검사 기록의 일치성

### 행위자와 신뢰 경계

| 행위자·경계                 | 예상하는 상황                                              | 필요한 통제                                                                     |
| --------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 워크플로 작성자 → 업로드    | 실수로 비밀정보를 포함하거나 의도적으로 위험한 노드를 삽입 | 원본 내용은 신뢰하지 않고 분석하며, 작성자의 설명으로 탐지를 자동 해제하지 않음 |
| 외부 호출자 → 워크플로 입력 | 요청·메일·파일·외부 문서의 값을 조작                       | 입력 출처와 위험 작업까지의 흐름을 분석                                         |
| 외부 데이터 → AI 도구       | 외부 텍스트의 지시가 도구 사용에 영향을 줄 가능성          | 정적 권한 조합과 승인 설정을 설명하고 실제 환경에 따라 달라지는 동작을 표시     |
| 업로드 파일 → 분석 프로세스 | 거대한 구조·복잡한 코드·비정상 문자열로 자원을 소모        | 파싱·시간·메모리·출력 제한, 실행 금지, 작업 격리                                |
| 작업 제어부 → 분석 프로세스 | 분석기가 서비스 전체 자격 증명을 갖게 되는 상황            | 작업별 파일만 제공하고 전체 DB·S3 권한을 분석 프로세스에 넘기지 않음            |
| 비공개 리비전 → 다른 사용자 | ID나 파일 해시를 알아내 비공개 정보에 접근                 | 소유권 검사, 비공개 중복 여부 비노출, 공개 대상의 명시적 선택                   |
| 분석 결과 → 브라우저        | 노드 이름·메모·출력에 포함된 스크립트나 민감값 노출        | 텍스트 렌더링·필요한 정제, 근거 마스킹, 공개용 결과 분리                        |
| 검사 기록 → 다운로드        | 검사 후 다른 파일이나 새 버전을 배포                       | 불변 파일·실제 내용 해시와 공개 기록을 결합                                     |

보안 워크플로 기능이 있는 템플릿과 악의적인 템플릿은 같은 노드를 사용할 수 있다. 외부 전송·명령 실행·공개 Webhook의 존재만으로 악의나 실제 악용 가능성을 확정하지 않는다.

## 3. 검사 항목과 도구의 역할

다음은 도입할 검사 범위의 제안이다. 표에 항목이 있다는 사실은 구현·노드 지원·정확도 검증이 끝났다는 의미가 아니다. 각 항목은 지원 목록과 합성 검증 결과가 갖춰진 뒤 제공 범위에 포함한다.

| 항목                          | 파일에서 확인할 내용                                            | 기존 도구 활용 후보                                   | 자체 구현과 판정 한계                                                                                                    |
| ----------------------------- | --------------------------------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 1. 비밀정보 노출              | 설정·헤더·코드·메모·고정 데이터의 키·토큰·비밀번호 후보         | Gitleaks                                              | JSON 위치 연결, 마스킹, 참조값과 실제 문자열 구분. 발견만으로 키의 유효성을 확정하지 않음                                |
| 2. 개인정보 포함              | 고정 데이터·설정·코드에 포함된 지원 유형의 개인정보 후보        | Presidio 선택 도입                                    | 대상 필드와 언어·유형 정의, 예시 데이터 처리. 한국어 개인정보 전체 탐지나 실제 인물 정보 여부를 보증하지 않음            |
| 3. 요청자 검증                | Webhook 등 입력 지점의 인증 설정, 위험 작업 전 검증 흐름        | FlowGuard·n8ncheck의 검증한 규칙을 비교 대상으로 활용 | 노드·버전별 설정, 검증 대상 값과 경로 해석. 앞단 인증은 별도 정보 없으면 미확인                                          |
| 4. 외부 전송                  | HTTP 목적지, 이메일 수신처, 메시지 채널, 전달되는 데이터        | URL·코드 패턴 검사 일부                               | 목적지 목록과 데이터 분류, 동적 목적지 표시, 사용자가 지정한 허용 대상과 비교. 정상 전송을 자동으로 유출이라 부르지 않음 |
| 5. SSRF                       | 외부 입력이 전체 URL·호스트·포트 등 요청 목적지에 영향을 주는지 | 기존 동적 URL 규칙, 코드 내부 분석 일부               | 입력 흐름과 허용 조건, 호스트와 경로·쿼리 구분. 실제 DNS·리다이렉트·네트워크 접근은 정적 검사만으로 확정하지 않음        |
| 6. SQL 인젝션                 | 외부 입력의 SQL 문자열 삽입, 지원하는 매개변수 바인딩           | Semgrep CE의 추출 코드 분석, 검증한 노드 규칙         | DB 노드·작업·버전별 쿼리와 바인딩 의미. 값 바인딩은 동적 식별자나 접근 권한 검증을 대신하지 않음                         |
| 7. 명령 주입·위험 코드        | 외부 입력이 명령·평가 실행 지점에 전달되는지                    | Semgrep CE, 검증한 FlowGuard 규칙                     | n8n 입력 표현식과 노드 간 흐름, 실행 위치의 설명. 고정 명령의 존재와 입력에 의한 주입을 구분                             |
| 8. 통신 설정                  | 평문 HTTP, 인증서 검증 비활성화, URL 내 인증정보                | Gitleaks 및 단순 설정 규칙                            | 노드·버전별 옵션, 내부 테스트 등 사용 조건. 실제 통신 경로나 모든 연동 라이브러리의 TLS 동작은 별도 확인                 |
| 9. 응답·로그 노출             | 전체 입력·DB 결과가 응답·메시지·로그로 전달되는지               | 코드 내부는 Semgrep CE 일부                           | 필드 단위 전달과 민감도 추적, 필요한 출력과 과도한 출력의 구분. 데이터의 실제 민감성은 미확인일 수 있음                  |
| 10. 커뮤니티·고권한·하위 노드 | 명령·SSH·파일 접근·외부 패키지·하위 워크플로·AI 도구 연결       | FlowGuard·Agentic Radar의 구조 분석 참고              | 사용자용 접근 범위 설명, 미지원 노드·미제공 의존성 표시. 설치 패키지나 실제 부여 권한을 파일 이름으로 추정하지 않음      |

### 도구 채택 기준

- 엔진 버전과 사용하는 룰의 출처·버전·변경 내역을 고정한다.
- 도구 라이선스와 룰 라이선스를 별도로 확인하고 서비스 제공에 맞는 조합을 사용한다.
- 외부 도구의 심각도와 문구를 사용자 판정으로 그대로 전달하지 않는다. 확인한 근거를 공통 결과 모델로 변환한다.
- 외부 규칙을 사용하기 전에 정상 사례·위험 사례·반례를 실행해 지원 범위를 확인한다.
- 업로드 내용으로 검사 설정, 실행 인자, 허용 목록, 탐지 제외 규칙을 변경할 수 없게 한다. 제품에서 제공할 예외 처리는 인증된 별도 정책 경로로 관리한다.
- Semgrep CE는 추출 코드 내부 분석을 보조한다. 함수 내부 중심인 CE의 범위를 n8n 노드 전체의 흐름 분석으로 표현하지 않는다.
- FlowGuard·n8ncheck의 전체 출력이나 SQL 관련 규칙을 모든 DB 노드에 적용 가능한 검증 결과로 취급하지 않는다.

### 추가 정보가 필요한 확장

| 확장                         | 필요한 정보·환경                                        | 제공 가능한 결과                                                                                         |
| ---------------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 알려진 패키지 취약점         | 실제 n8n·커뮤니티 패키지 버전, 패키지 목록이나 lockfile | OSV-Scanner 등으로 해당 버전의 알려진 취약점 확인. JSON의 노드 버전을 설치 패키지 버전으로 치환하지 않음 |
| 운영 인스턴스 점검           | 사용자가 허용한 인스턴스 접근과 환경 정보               | n8n audit 등 별도 점검 결과 연결. 업로드 파일 검사와 출처·대상을 구분                                    |
| AI 도구 오용·프롬프트 인젝션 | 모델, 도구 권한, 승인 설정                              | 권한 조합과 승인 경계에 대한 근거. 실행 환경에 따라 달라지는 부분은 미확인으로 표시                      |

## 4. 지원 범위와 JSON 해석

### 지원 목록은 검사 기능의 일부다

노드 지원 여부를 이름 하나로 표시하지 않는다. 최소한 다음 조합을 관리한다.

- 노드 종류와 노드 버전
- 작업 종류와 사용 옵션
- 읽는 필드, 쓰는 필드, 표현식 처리 범위
- 제어 흐름과 데이터 흐름의 전달 규칙
- 인식하는 방어 조건과 적용 가능한 문맥
- 지원하지 않는 조합과 필요한 외부 정보
- 해당 조합을 검증한 합성 사례

정확한 최초 지원 목록은 별도 구현 이슈에서 확정한다. 미지원 버전을 가장 가까운 버전으로 조용히 해석하지 않는다. 이전 버전의 분석기를 재사용한다면 호환성 근거와 검증 사례가 필요하다.

### 파싱과 정규화

1. 파일 크기와 구조 제한 안에서 JSON을 파싱한다. 허용 깊이·노드 수·문자열 크기·중복 키 등 모호한 입력의 처리 기준은 업로드 계약에서 정한다.
2. 원본 바이트를 보존하고 실제 내용 해시를 확인한다. 정규화한 그래프의 해시는 별도 용도로 취급한다.
3. 노드 식별자·이름·종류·버전·활성 상태·설정과 연결을 정규화한다.
4. 분기와 출력 위치를 보존한다. 일반 실행 연결, AI 도구 연결, 표현식으로 직접 참조하는 다른 노드의 데이터 의존성을 구분한다.
5. 분석한 모든 값과 결과를 원본 JSON의 정확한 위치에 연결한다. 배열 순서만으로 노드의 장기 식별자를 만들지 않는다.
6. 구조 해석에 실패한 부분을 기록한다. 일부 필드만 읽었다면 워크플로 전체를 분석했다고 표시하지 않는다.

비활성 노드에도 비밀정보는 남아 있을 수 있으므로 파일 내용 검사는 수행한다. 실행 경로 분석에서는 비활성 상태와 관련 가정을 표시하고, 새 리비전에서 활성화되면 변화로 보고한다.

## 5. 데이터 흐름과 방어 조건

### 두 가지 속성을 별도로 추적한다

| 속성             | 질문                                                | 예시                                       |
| ---------------- | --------------------------------------------------- | ------------------------------------------ |
| 외부 조작 가능성 | 공격자나 신뢰하지 않는 출처가 값을 정할 수 있는가?  | Webhook 본문·쿼리, 외부 문서의 문자열      |
| 민감도           | 이 값이 특정 대상으로 전달되면 문제가 될 수 있는가? | 고객 정보, 비밀정보 후보, 내부 업무 데이터 |

외부 입력이 항상 개인정보인 것은 아니며, 내부 DB 결과가 항상 비민감한 것도 아니다. 출처의 신뢰와 데이터 민감도를 하나의 태그로 합치지 않는다. 값의 민감도가 필드 이름에서 추정된 경우에는 추정임을 표시한다.

### 분석의 기본 단위

지원하는 입력 출처에서 필드의 전달·변형·병합을 추적하고, HTTP 요청·DB 쿼리·명령·응답 등 위험 작업에 도달하는 경로를 찾는다. 모든 입력을 무조건 위험하다고 처리하거나, 모든 연결된 노드를 같은 데이터 흐름으로 취급하지 않는다.

정적 분석에 필요한 제한된 표현식 구문을 해석할 수 있으나, 사용자 표현식을 평가하거나 Code 노드를 실행해서 값을 구하지 않는다. 임의 코드나 미지원 변환을 통과하면 그 이후 값의 출처·형태에 대한 불확실성을 전달한다.

### 방어 조건을 인정하는 기준

- 검증한 값과 위험 작업에 사용되는 값이 같아야 한다.
- 관련 위험 작업으로 이어지는 모든 지원 경로에 검증이 적용되어야 한다. 검증을 우회하는 다른 분기는 별도로 분석한다.
- 방어는 해당 문맥에 맞아야 한다. SQL 값 바인딩, URL 목적지 제한, 명령 인자 처리를 서로 바꿔 인정하지 않는다.
- 검증 이후 값이 다시 결합·변경되면 원래 방어가 여전히 적용되는지 확인한다.
- IF 노드가 있다는 사실이나 검증처럼 보이는 노드 이름만으로 안전한 경로로 분류하지 않는다.
- 코드 주석·메모·작성자의 설명은 의도에 관한 정보다. 검증이 구현됐다는 증거로 사용하지 않는다.

### 주요 유형별 판정 경계

**SQL:** 값을 바인딩하는 안전 패턴과 쿼리 문자열·구조를 조합하는 패턴을 구분한다. 바인딩 옵션이 존재해도 실제 쿼리와 연결되는지 확인한다. 바인딩으로 특정 주입 경로가 해소돼도 사용자가 타인의 데이터를 조회할 수 있는 접근 제어 문제까지 해소됐다고 설명하지 않는다.

**SSRF:** 고정 호스트의 경로나 쿼리에 값이 들어가는 경우와 전체 URL·호스트가 외부 입력으로 결정되는 경우를 구분한다. 목적지 제한은 요청에 사용되는 값에 적용되어야 한다. DNS 해석·리다이렉트·실제 내부망 차단이 확인되지 않았다면 이를 남긴다. 정적 검사를 위해 사용자가 넣은 URL에 접속하지 않는다.

**명령 실행:** 명령 실행 기능의 존재, 외부 입력의 명령문 결합, 실행 환경의 권한을 구분한다. 실행 위치와 계정 권한을 알 수 없다면 가능한 영향은 조건부로 설명한다.

**응답·외부 전송:** 출력 필드의 출처와 민감도, 목적지, 사용 정책을 함께 제시한다. 민감도나 수신 대상의 소유권을 확인하지 못했다면 유출로 확정하지 않는다.

## 6. 검사 결과 계약의 개념

아래 항목은 API·DB 필드명을 확정한 스키마가 아니다. 프론트·백엔드·워커가 계약을 만들 때 보존해야 할 정보다. 실제 필드명·자료형·enum·호환성 규칙은 계약 작업에서 정한다.

### 검사 실행에 필요한 정보

| 정보                                      | 보존 이유                                           |
| ----------------------------------------- | --------------------------------------------------- |
| 워크플로·리비전·원본 파일 해시            | 결과의 정확한 대상 식별                             |
| 파서·노드 어댑터·분석 도구·룰 묶음의 버전 | 과거 결과의 해석과 재검사 비교                      |
| 검사 범위와 입력된 사용 환경 정보         | 무엇을 근거로 어디까지 판단했는지 표시              |
| 시작·종료와 실행 결과                     | 장애·시간 초과를 정상 완료와 구분                   |
| 항목·노드별 분석 범위와 한계              | 미지원·미제공 의존성·추적 불가 구간 표시            |
| 도구별 성공·실패와 사용 가능한 부분 결과  | 일부 도구가 실패해도 남은 증거를 정확한 범위로 제공 |

### 탐지 항목에 필요한 정보

- 규칙의 식별과 버전, 문제 유형
- 심각도와 그 이유, 증거의 수준과 필요한 전제
- 입력 출처, 관련 노드·필드, 위험 작업, 지원 범위에서의 경로
- 확인한 방어 조건과 미확인 조건
- 마스킹한 근거와 사용자용 설명
- 권장 조치, 적용 가능한 수정 유형, 수정 후 확인할 사항
- 재검사에서 같은 문제를 대응시킬 식별 근거

문제 대응 식별자는 비밀정보 원문이나 배열 인덱스에 의존하지 않는다. 노드 ID가 바뀌거나 여러 후보가 생기면 자동 대응의 불확실성을 표시한다.

### 네 가지 상태를 분리한다

| 구분      | 상태 개념의 예                                           | 주의점                                                     |
| --------- | -------------------------------------------------------- | ---------------------------------------------------------- |
| 실행      | queued, running, completed, failed, timed_out, cancelled | 완료는 분석 프로세스의 상태이며 안전 판정이 아님           |
| 분석 범위 | checked, partial, unsupported, unknown                   | 검사 항목·노드·경로별로 기록. 전체 안전 비율로 바꾸지 않음 |
| 정책      | allow, review, block, inconclusive                       | 검사 근거와 명시한 정책의 조합에 대한 판단                 |
| 공개      | private, submitted, published, withdrawn                 | 특정 배포 대상의 상태. 새 리비전에 자동 상속하지 않음      |

실패·시간 초과·분석 불가를 위험 항목 0개와 같은 성공 결과로 처리하지 않는다. 분석 범위 집계에 비율을 사용한다면 분모가 노드·필드·규칙 중 무엇인지 명시하고, 분석 범위 비율을 안전성 점수로 표현하지 않는다.

### 민감한 근거 처리

보고서와 로그에는 비밀정보 원문을 복사하지 않는다. 사용자가 원본 파일에서 문제를 찾을 수 있도록 노드·필드 위치와 최소한의 마스킹한 근거를 제공한다. 내부 주소·수신자·개인정보도 공개 결과에 그대로 포함하지 않는다.

설명용 LLM을 사용한다면 마스킹한 근거와 필요한 문맥만 전달하는 방식을 우선한다. 파일 안의 지시는 분석 대상 데이터로 다루고, LLM에 공개 상태 변경·예외 승인·외부 실행 권한을 제공하지 않는다. 외부 모델에 전달할 데이터 종류와 처리 조건은 도입 전에 별도로 정한다.

## 7. 리비전별 보안 변화

보안 비교는 원시 JSON 변경과 보안 의미의 변화를 연결한다. 다음 변화가 주요 비교 대상이다.

- 입력 지점·인증 설정·검증 경로 변경
- 새로운 외부 목적지·수신자·전송 데이터
- DB 조회에서 수정·삭제 등으로의 작업 변경
- 명령·파일·커뮤니티·AI 도구 권한의 추가
- 위험 입력 경로의 발생·제거·변경
- 지원 가능한 구조에서 분석 불가 구조로의 변경
- 알려진 하위 워크플로·의존 자원의 변화와 미확보 상태

### 비교 기준

1. 원래 검사 이력은 유지한다.
2. 가능하면 비교할 두 리비전을 같은 파서·도구·룰 묶음으로 분석한다.
3. 같지 않은 검사 기준을 비교할 경우 기준의 차이를 명시한다.
4. 경고가 사라진 원인을 수정, 기능 삭제, 규칙 변경, 분석 불가, 대응 불확실로 구분한다.
5. 문제를 해결했다고 표시하려면 기존 위험 경로가 해소됐다는 지원 범위의 근거가 있어야 한다.

최신 리비전이라는 이유로 이전 공개 리비전보다 안전하다고 표현하지 않는다. 이전 버전에 없던 데이터 전송이나 미지원 코드가 추가되면 그 변화를 사용자에게 제시한다.

## 8. 수정안과 재검사

수정안은 적용 대상 리비전과 파일 해시, 변경 전제, 변경 내용, 기대 효과, 사용자가 조정할 후속 설정을 포함한다. 예를 들어 인증 설정을 추가하면 호출하는 시스템에도 설정 변경이 필요할 수 있다.

### 수정 적용 흐름

1. 원본 리비전과 지원되는 수정 유형을 확인한다.
2. 변경할 노드·필드와 예상 영향을 사용자에게 보여준다.
3. 사용자가 적용을 요청하면 기준 파일과 수정 전제가 일치하는지 먼저 확인한다. 기준이 바뀌면 기존 수정안을 그대로 적용하지 않는다.
4. 확인을 통과하면 원본을 덮어쓰지 않고 새 리비전을 만든다.
5. 새 파일을 재검사한다. 이전 검사 표시를 복사하지 않는다.
6. 해결된 문제, 새 문제, 남은 조건, 분석 범위 변화를 보여준다.
7. 지원하는 합성 사례에서는 정상 업무 동작과 수정한 방어 조건을 함께 검증한다.

자동 수정의 지원 단위는 노드·버전·작업·패턴 조합이다. 외부 자격 증명 참조나 업무 목적을 추정해 임의로 대체하지 않는다. 비밀정보 제거가 필요하면 필요한 자격 증명 설정과 키 폐기·재발급 같은 후속 조치를 안내하고, 실제 외부 계정 작업은 별도 사용자 행위로 둔다.

검사 결과만 사라지게 하는 수정은 성공 기준이 아니다. 기능을 제거하거나 실행 경로를 끊은 수정이라면 업무 동작이 달라졌음을 표시한다.

## 9. 사용 정책과 공개

### 기술적 분석과 정책 판단

분석 엔진은 파일에서 확인한 사실과 위험 경로를 만든다. 정책은 허용 목적지, 데이터 분류, 필요한 인증·승인 조건, 미확인 항목의 처리 방식으로 사용 가능 여부를 평가한다.

사용자가 입력한 환경 정보는 선언으로 표시한다. 별도 연동으로 확인한 정보는 확인 방법·시점·대상과 함께 기록한다. 작성자가 앞단 인증이 있다고 기재했다는 이유만으로 파일의 인증 미확인 표시를 없애지 않는다.

정책 예외는 판단자·사유·범위·필요한 유효 기간을 가진 별도 기록으로 관리하는 방향을 제안한다. 원래 탐지 결과는 보존한다. 정책 변경과 오탐 판단이 과거의 기술적 검사 사실을 수정하지 않게 한다.

### 공개 대상의 조건

- 공개 기록은 정확한 리비전·파일 해시·검사 실행·정책 평가를 가리킨다.
- 공개할 파일을 정제하거나 수정해 바이트가 바뀌었다면 새 리비전을 생성하고 다시 검사한다. 공개 기록은 변경된 리비전과 그 파일의 검사·정책 평가에 연결한다.
- 새 리비전을 만들었다고 기존 공개 버전을 자동 교체하지 않는다.
- 공개 리비전에서 비공개 부모·원본·소유자의 내부 정책·민감한 상세 보고서로 접근할 수 없게 한다.
- 공개용 보고서는 공개가 허용된 정보만 포함한다. 원본 검사 이력의 무조건적인 공개 복사본으로 만들지 않는다.
- 다른 사용자의 재사용은 별도 소유 워크플로와 출처 관계로 관리한다. 출처 정보가 비공개 계보 열람 권한을 뜻하지 않는다.

어떤 심각도·증거 수준·미확인 조건에서 공개를 허용·검토·차단할지는 팀이 정해야 할 제품 정책이다. 정책이 정해지기 전의 설계 기본값은 기존 개인 비공개 흐름을 유지하는 것이다. 공개 판정을 통과하더라도 사용 환경에 따라 달라지는 권한·네트워크·실제 자격 증명의 안전성을 보증한다고 표시하지 않는다.

파일 해시나 서명은 검사 기록과 파일의 연결을 확인하는 수단이다. 그것만으로 검사 품질이나 안전성이 증명되는 것은 아니다.

## 10. 검사 플랫폼 자체의 통제

시스템 배치와 권한 모델은 [ARCHITECTURE.md](ARCHITECTURE.md)에서 관리하며, 검사 기능은 다음 요구를 충족해야 한다.

- 업로드 제한은 HTTP 수신·파싱·분석 각 단계에서 적용한다. 압축 파일을 지원한다면 해제 한도도 별도로 설계한다.
- 작업별 자원·시간·출력 한도와 사용자별 요청량을 정한다. 실패한 분석기는 상태와 사유를 반환한다.
- 정적 분석 프로세스는 외부 네트워크를 기본 차단하고 신뢰된 도구·룰만 사용한다.
- 업로드가 요구하는 패키지를 설치하거나 실행하지 않는다.
- 워커의 작업 요청과 결과 제출은 서비스 인증과 작업 범위 확인을 거친다.
- 결과 제출 시 실행 시도·대상 파일·도구 및 규칙 버전을 확인한다. 중복 제출과 늦게 도착한 이전 시도가 결과를 바꾸지 못하게 한다.
- 노드 이름·메모·코드·도구 오류·LLM 설명은 모두 신뢰하지 않는 표시 데이터로 취급한다.
- 검사·수정안 조회와 다운로드는 식별자를 아는 것만으로 허용하지 않는다.
- 로그에는 작업 식별과 제한된 오류 정보를 남기며 입력 본문·토큰·다운로드 URL·원문 비밀정보를 남기지 않는다.

## 11. 검증 계획과 완료 기준

### 합성 사례 구성

각 지원 규칙은 위험 사례, 정상 사례, 분석 불가 사례를 함께 가진다. 노드 이름·배열 순서·서식만 바뀐 사례도 포함해 우연한 문자열이나 위치에 의존하지 않는지 확인한다.

| 사례                                                 | 확인할 결과                                                        |
| ---------------------------------------------------- | ------------------------------------------------------------------ |
| 실제 형식의 합성 토큰이 설정·메모·고정 데이터에 존재 | 탐지 위치는 정확하고 화면·로그에는 원문이 노출되지 않음            |
| 자격 증명 이름·명백한 예시 문자열                    | 실제 유효한 비밀정보로 확정하지 않음                               |
| 외부 입력의 SQL 직접 삽입                            | 지원 경로와 위험 작업을 연결해 설명                                |
| 같은 기능을 값 바인딩으로 구현                       | 해당 주입 경로를 위험한 문자열 삽입으로 분류하지 않음              |
| 쿼리 매개변수 옵션만 있고 실제 쿼리 연결은 다름      | 옵션 존재만으로 방어가 성립했다고 처리하지 않음                    |
| IF가 다른 필드를 검증하거나 우회 분기가 존재         | 위험 경로가 남아 있음을 표시                                       |
| 고정 호스트의 경로와 외부 입력이 정하는 전체 URL     | 두 위험 형태를 구분                                                |
| 검증 후 URL 또는 명령 값이 다시 변형됨               | 방어 적용이 유지되는지 재평가하고 미지원이면 한계를 표시           |
| 고정 명령 실행과 외부 값이 결합되는 명령             | 기능 위험과 입력 주입 위험을 구분                                  |
| 정상 업무의 외부 전송                                | 목적지·데이터·정책을 설명하며 악의적 유출로 자동 확정하지 않음     |
| Code 또는 미지원 노드가 흐름 중간에 존재             | 분석 불가가 사라진 경고나 안전으로 표현되지 않음                   |
| 미제공 하위 워크플로 또는 미지원 노드 버전           | 전체 분석 완료로 표시하지 않음                                     |
| 수정으로 위험 경로를 해소한 새 리비전                | 정확한 수정본을 재검사하고 해결 근거를 제시                        |
| 규칙 변경 때문에 과거 경고가 사라짐                  | 코드 수정에 따른 해결과 구분                                       |
| 수정이 원래 기능을 제거함                            | 경고 감소와 업무 동작 변경을 함께 표시                             |
| 새로운 리비전에 외부 전송 노드 추가                  | 이전 공개 버전과의 보안 변화로 표시                                |
| 다른 사용자의 검사·수정안·비공개 부모 ID 요청        | 소유권 또는 공개 범위에 맞게 접근 거부                             |
| 원본 해시 불일치·중복 제출·이전 작업의 지연 결과     | 다른 파일의 결과 연결이나 최신 상태 덮어쓰기 방지                  |
| 분석기 실패·시간 초과·잘못된 출력                    | 검사 실패나 부분 분석으로 표시하며 위험 0개 성공으로 처리하지 않음 |
| 검사 후 파일 변경 또는 공개 전 정제                  | 기존 검사로 새 파일을 공개하지 않음                                |

### 동적 검증의 경계

실행 검증은 팀이 관리하는 합성 워크플로와 테스트 전용 서비스에서 수행한다. 합성 데이터와 테스트 전용 계정으로 실행하며, 정상 동작과 방어 조건의 기대 결과, 사용한 환경, 대상 파일 해시를 함께 남긴다.

임의 업로드 파일의 실행 서비스를 제공하는 것은 별도 제품 범위다. 이 설계의 정적 분석 워커에 암묵적으로 포함하지 않는다.

### 품질 평가

- 규칙·노드·버전별로 라벨이 확인된 평가 사례에서 정탐·오탐·미탐을 기록한다.
- 정확도나 재현율을 제시할 때 평가 집합과 분모, 미지원 처리 방법을 함께 밝힌다.
- 분석 불가와 환경 정보 부족을 정상 사례로 계산하지 않는다.
- 수정 성공은 위험 해소와 지원하는 정상 동작 보존을 함께 평가한다.
- 사용자 평가에서는 위험 이해, 필요한 조치 발견, 수정·재검사 완료 여부를 확인한다.
- 실제 공격 가능성을 검증하지 않은 전체 공개 템플릿의 경고 수를 실제 취약점 발생률로 표현하지 않는다.

### 첫 통합 시연의 완료 조건

합성 파일 업로드에서 특정 리비전 검사, 노드·필드 근거 표시, 수정 리비전 생성, 재검사, 보안 변화 비교까지 연결한다. 공개 단계의 정책이 결정되고 구현되면 검사한 특정 파일의 공개·다운로드까지 검증한다. 실제 구현 상태는 기능별 증거에 따라 PLAN에서 갱신한다.
