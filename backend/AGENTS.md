# Backend harness

Read root AGENTS.md first. Work inside backend unless an API change affects the frontend, then say so in the task report.

- Java 25, Spring Boot 4.0.10, Gradle wrapper only. Package by domain (`auth`, `health`, `workflow`, `analysis`), not global controller/service folders. Inside a domain use the same sub-packages everywhere: `api` (controllers, exception handlers, request/response records), `service` (business rules, validators, domain exceptions), `storage` (external storage ports and adapters such as S3), `queue` (external queue ports and adapters such as SQS), `config` (framework wiring). `common` holds cross-domain code with the same sub-packages (`common/api` error body and global handler, `common/config` OpenAPI, `common/events` cross-domain transaction events, `common/logging` request-id filter); a domain must not depend on another domain's internals. Create a sub-package only when it has a class; do not add a repository layer until persistence outgrows `JdbcClient` in services. Test packages mirror the class under test, and the Postgres-backed migration test stays at the domain root.
- Windows: `./gradlew.bat bootRun`; Linux/macOS: `./gradlew bootRun`.
- Verify: `./gradlew spotlessCheck test bootJar` (use gradlew.bat on Windows). Format: `./gradlew spotlessApply`.
- Google Java Format is authoritative. No hand-maintained conflicting Java style rules.
- Supabase issues and rotates tokens. This API validates bearer access tokens via asymmetric JWKS, issuer, audience, expiry and subject. Never issue a second JWT or accept refresh tokens as API credentials.
- No server login sessions or authentication cookies. CSRF is disabled only because this API accepts bearer headers; revisit if cookies become credentials.
- CORS origins are explicit. Do not use wildcard origins for convenience.
- Identity comes from verified subject, never a client-supplied owner ID. Future workflow queries must enforce owner/shared visibility and revision ownership.
- Flyway manages workflow and version metadata tables in the backend-only `workflow_hub` PostgreSQL schema. Keep this schema out of Supabase Data API exposure. `POST /api/workflows` stores the original file in private S3 (`WORKFLOW_BUCKET` is required at startup with the default AWS credential chain) and creates workflow `v1` plus an idempotency record in one transaction. Owner-scoped list, detail and version queries use keyset pagination for both lists (default 20, maximum 100). Workflow creation time is backfilled from v1 by V3. Version registration rechecks the applicable base and writes the new version and idempotency record in one transaction. Version rows also record the server-computed SHA-256 and byte size of the exact bytes passed to S3 (`content_sha256`, `size_bytes`, V6; NULL means unrecorded for versions that predate V6, never trust a client hash or S3 ETag). Download checks ownership, version membership and download availability before reading from S3. Uploads and version registration first commit a `workflow_hub.pending_objects` row (V7) before writing to S3 and delete it in the same transaction as the version insert; `WorkflowObjectCleanup` (scheduled, `PENDING_OBJECT_GRACE` default 30m, `CLEANUP_RETRY_DELAY` default 5m, `PENDING_OBJECT_CLEANUP_INTERVAL` default 10s; the grace must be at least twice `S3_CALL_TIMEOUT`) deletes unreferenced objects only for rows past `cleanup_after`, keeps referenced ones and retries failures. It assumes S3 versioning is off. Original JSON must never be executed, modified or logged.
- Deletion (#37, V8): deletes are soft (`deleted_at`), never remove rows, so version numbers are never reused (`nextLabel` in `WorkflowVersionService` reads all rows incl. deleted/purged; the base check and every read path read only `deleted_at IS NULL`). Each version has its own `delete_after` (`WORKFLOW_DELETE_GRACE`, default 7d); a workflow delete stamps the workflow and its alive versions with one shared `deleted_at`, and a workflow restore revives only versions whose `deleted_at` equals the workflow's. Deleting the last alive version deletes the workflow, unless the request sends `allowWorkflowDelete=false` (#46): then it is refused with `409 LAST_VERSION_REMAINING` under the workflow lock and nothing changes, so a delete confirmed for one version never removes the workflow. `WorkflowDeletionService` locks the workflow row first, then version rows (purge `markPurged` follows the same order); restore checks state, calls `HeadObject` outside any lock, then re-checks under the lock; a missing object only fails the restore and never changes the row (a 404 can be a bucket misconfiguration), the purge job handles it after the deadline. A retry of a committed version registration (same Idempotency-Key) returns the original result even if the workflow was deleted afterwards. `WorkflowVersionPurge` claims one due row by committing `delete_started_at` before `DeleteObject` (after that restore is refused), then sets `purged_at` and nulls the key/hash/size (title is nulled once every version is purged). `HeadObject` needs `s3:ListBucket` to tell 404 from 403; `S3WorkflowObjectStore.size` never turns 403 into "missing". Deleted rows are listed only with `includeDeleted=true` and only while restorable.
- n8n JSON limits (#35): `N8nWorkflowValidator` is the only place that applies them, and both the first upload and version comparison (candidate and the stored base version) go through it. `WorkflowLimits` holds max depth/nodes/connections (defaults 64/300/1500, env `WORKFLOW_MAX_DEPTH`/`WORKFLOW_MAX_NODES`/`WORKFLOW_MAX_CONNECTIONS`, nodes/connections below 1 or depth below 6 fail startup, since a workflow with a connection is at least 6 deep). A file exactly at a limit passes; one over it gets `422 WORKFLOW_LIMIT_EXCEEDED` with only the limit kind and value in the message. Depth is enforced by the parser (`StreamReadConstraints`) while parsing; a depth overrun is told apart from other Jackson constraint failures by following tokens with a probe parser that uses the same encoding detection (UTF-8/16/32), never by the exception text or raw bytes. Validation must stay before any S3 write, `pending_objects` row or DB write so a rejected request leaves nothing behind. Values and measurements live in docs/INPUT_LIMITS.md; re-measure latency before raising them.
- Security scans (#39, #57, V9): `dev.workflowhub.analysis` owns user scan APIs (`/api/workflows/{workflowId}/versions/{versionId}/scans/**`, including `/latest` returning `200 { "data": null }` when no scan exists and `/scans/{scanRunId}/report` lazy-loading `serviceReport` from private S3 after ownership check) and worker internal APIs (`/internal/worker/v1/tasks/{taskId}/attempts/{attemptId}/file|heartbeat|result`). Worker internal routes use a separate `@Order(1)` `SecurityFilterChain` matching `/internal/**` with service-only Bearer tokens (`WORKER_API_TOKENS`, comma-separated for rotation, required at startup) and never accept Supabase user JWTs. `SCAN_QUEUE_URL` is also required at startup and dispatches `ScanTaskMessage` to SQS via `ScanTaskQueue`. Lightweight 4-axis status, summary, error, and private S3 keys stay in PostgreSQL (`scan_runs`, `analysis_jobs`, `analysis_job_attempts`, `scan_request_idempotency_keys`); `serviceReport` and raw `assessment` JSON are stored in private S3 guarded by `pending_objects` and cleaned up on version purge. Workflow/version deletion publishes `WorkflowDeletionEvent` inside the deletion transaction so `ScanCancellationListener` atomically cancels active scans; `ScanLeaseRecovery` re-queues expired leases and stale `queued` jobs (`SCAN_QUEUED_TIMEOUT`) up to `SCAN_MAX_ATTEMPTS` (default 3) or marks them `timed_out`. All SQS sends go through `ScanTaskDispatcher`, which records `analysis_job_attempts.dispatched_at`; a failed send never fails the scan or changes an accepted worker response, and `ScanLeaseRecovery` resends an unconfirmed `queued` attempt with the same `attemptId` after `SCAN_DISPATCH_RETRY_DELAY` (default 1m, must exceed `SQS_CALL_TIMEOUT` and be shorter than `SCAN_QUEUED_TIMEOUT`). A first-request dispatch failure deletes the run only while the job still points at that unconfirmed attempt, and a same-key replay before the first send is confirmed gets `503 SCAN_DISPATCH_UNAVAILABLE`. Worker endpoints lock the `analysis_jobs` row first and read attempt state and lease validity in a separate statement (READ COMMITTED would otherwise return stale joined rows); `HEAD .../file` is rejected with 405. Cross-domain pending-object protection goes through `common.storage.PendingObjectRegistry`. Version purge caps S3 delete calls per run (`MAX_DELETE_CALLS_PER_RUN`), clears each scan row's keys as its objects are deleted, marks the version purged only after all objects are gone, and picks never-attempted rows before retries so one failing version cannot block others.
- Full backend verification requires Docker for PostgreSQL Testcontainers. The test database is disposable and independent of runtime database configuration.
- No production credentials needed for tests. MockMvc JWT tests cover endpoint behavior; validator unit tests cover claims. Real Google callback/JWKS/RTR integration needs an actual configured Supabase project.
- SQL access uses Spring JDBC (`JdbcClient`, explicit `spring-boot-starter-jdbc`) with Flyway-owned schema. JPA/Hibernate is deliberately not used: the schema is a few tables written by explicit transactions, idempotency depends on exact SQL and unique constraints, and entity mapping would add lazy-loading and dirty-checking behavior without removing code. Revisit JPA when listing/detail queries need relations or paging across many entities.
- Logging: every line is `event=<domain.action> key=value`; `requestId` comes from the MDC (`X-Request-Id` filter, also in the response header and `ApiError.requestId`). Log IDs, object keys, sizes, durations and exception stack traces; never log file content, titles, tokens, auth headers, presigned URLs or query strings. Expected client errors are WARN, unexpected failures ERROR with the exception. Add an `event=` line when you add a step that can fail or that you would want to find at 3 a.m.
- Swagger UI (`/swagger-ui.html`) and `/v3/api-docs` exist only when `API_DOCS_ENABLED=true` (off by default, including in `.env.example`; set it to true only locally). The OpenAPI annotations on controllers are the single API reference (there is no separate contract file): keep summaries, request/response examples and every status code up to date with the behavior.
- Code comments are Korean and only where the reason is not obvious from the code.
- Update the OpenAPI annotations with endpoint changes, add meaningful authorization/error tests, report exact checks and limitations.
