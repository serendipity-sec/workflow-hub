# 차별화 근거와 검증 계획

> 팀 검토용 제안 · 자료 검토일 2026-11-22 (한국 시간) · 구현·비교 성능·사용자 효과는 미검증

## 1. 현재 내릴 수 있는 결론

기존 플랫폼과 도구는 보안 감사, 템플릿 제출 검토, 노드 관계 분석, 버전 승인, 공유·설정 안내를 이미 제공한다. 관련 보안 서비스에는 검사 결과에서 완화와 재검증으로 이어지는 흐름도 있다. 이 기능들을 비교의 출발점으로 삼는다. Workflow Hub의 효과는 6절의 가설을 평가한 결과로 설명한다.

Workflow Hub의 제안은 **외부 n8n 파일을 자신의 계정·데이터에 연결하기 전에, 사용자가 노드별 위험 근거와 분석 한계를 이해하고 수정 전후의 보안 변화를 확인하며, 검사한 정확한 버전을 선택하도록 돕는 것**이다. 이 흐름이 기존 도구의 정상적인 사용보다 판단과 조치를 개선하는지는 별도 평가가 필요하다. “기존 공유 플랫폼은 보안 검사를 하지 않는다”, “그래프 분석·버전 관리·수정 안내를 처음 제공한다”는 주장은 사용하지 않는다.

현재 제품 결정은 워크플로별 불변 `Version`(예: `v1`, `v1.1`, `v2`)을 관리하고, 다른 사용자가 파생한 워크플로는 독립 워크플로의 `v1`로 시작하는 것이다. 리비전 트리·부모 계보를 확정 기능으로 전제하지 않는다. 아래의 출처 기록, 수정 전후 비교, 검사 결과와 공개 파일의 연결은 이 버전 모델 위에 추가할 **보안 기능 제안**이다.

이 문서는 경쟁 기능의 조사, 제품 가설, 입증 방법을 관리한다. 구현 방법은 [SECURITY_DESIGN.md](SECURITY_DESIGN.md), 시스템 경계는 [ARCHITECTURE.md](ARCHITECTURE.md), 단계와 결정 상태는 [PLAN.md](PLAN.md)에서 관리한다. 현재 상태는 기능 설계와 평가 계획 단계다.

## 2. 누구의 어떤 문제를 검증할 것인가

우선 대상은 다른 사람이 만든 n8n 템플릿을 자신의 계정·DB·업무 데이터에 연결하는 사용자다. 다음 대상은 이를 배포하는 제작자와 팀 검토자다. 사용자의 개발 경험은 평가에서 구분한다.

검증하려는 문제는 다음과 같다.

- 가져온 파일에서 실행 주체, 전송 대상, 위험 작업과 필요한 권한을 파악하기 어려운가?
- 경고를 읽어도 어떤 노드와 값을 바꿔야 하는지 판단하기 어려운가?
- 업데이트가 목적지·인증·권한·입력 흐름을 어떻게 바꾸는지 놓치는가?
- 경고를 없애는 과정에서 원래 업무 동작을 망가뜨리거나, 검사한 파일과 다른 파일을 사용하는가?
- 개인정보나 업무 구조를 담은 파일을 별도 플랫폼에 업로드할 의향이 있는가?

문제의 빈도와 심각도, 현재 해결 방식, 제품 전환·지불 의사는 검증할 가설이다. 사용자 수요와 사업성은 사용자 조사에서 확인한다.

## 3. 비교 자료를 읽는 기준

| 구분                    | 이 문서에서의 의미                                          | 가능한 주장                                |
| ----------------------- | ----------------------------------------------------------- | ------------------------------------------ |
| 공식 문서·소스에서 확인 | 제공자가 설명한 기능이나 특정 코드의 동작을 읽음            | 해당 자료와 확인 시점에 기능·구현이 존재함 |
| 조사 범위에서 미확인    | 검토한 페이지에서 해당 기능을 찾지 못함                     | 검토한 자료에서 미확인으로 기록            |
| 설계상의 추론           | 확인한 기능·경계를 바탕으로 위험이나 기회를 해석            | 추론과 성립 조건을 함께 설명               |
| 제품 가설               | Workflow Hub가 사용자 판단·분석·조치를 개선할 것이라는 제안 | 비교 실험으로 검증할 대상                  |
| 실증 결과               | 명시한 버전·사례·환경에서 실제 측정                         | 그 범위와 한계를 포함한 성능·효과 주장     |

비교 범위는 n8n 공식 기능, n8n 공유 플랫폼·재배포 카탈로그, 공개 검사기, AIronClaw의 공개 자료, Make·Zapier·GitHub의 공유와 보호 기능이다. 아래 자료의 검토일은 별도 표시가 없으면 2026-11-22다. 공개 문서의 기능 설명, 읽은 소스의 구현, 제한된 재현 결과, 운영 중 사고를 구분한다. 출시 전에는 링크·요금제·지원 버전·기능 변경을 재확인한다.

**미확인은 부재의 증명이 아니다.** 특정 플랫폼에서 취약·악성 파일이 유통됐다는 주장은 원본 플랫폼·파일·버전·관찰 시점과 위험 근거가 연결될 때만 한다. npm 패키지 사고나 n8n 엔진 취약점을 곧바로 템플릿 마켓의 악성 JSON 유통 증거로 바꾸지 않는다.

#### 코드에서 얻은 구체적인 검증 후보

검토한 FlowGuard 입력 검증 규칙은 경로에서 IF·Switch·Filter 유형을 만나면 해당 탐색을 종료한다. 해당 함수에서 검증 대상 값과 위험 작업의 실제 입력이 일치하는지 해석하는 로직은 확인하지 못했다. 입력 검증이 다른 필드에 적용되거나, 검증 후 원본을 다시 참조하는 합성 사례로 비교한다. 관찰한 범위는 **한 규칙의 소스**다. 다른 규칙이 같은 사례를 경고할 가능성을 포함해 전체 도구의 실제 출력은 고정한 설정에서 별도로 측정해야 한다. 확인한 Git blob SHA는 `4f47f2b3ad543157f95db2dac040c258f4855a83`이다. [FlowGuard 고정 커밋의 규칙](https://github.com/MohibShaikh/FlowGuard/blob/03b348d008eaafdebc3650973561d8091af1d8c8/src/rules/owasp/missing-input-validation.ts)

n8ncheck에서 확인한 BigQuery 검사 파일은 BigQuery·BigQueryTool의 설정과 동적 쿼리 구성을 다룬다. DB별 비교 평가에서는 동적 구성, 값 바인딩, 입력 출처를 각각 확인한다. 다른 DB 노드와 시나리오의 지원 범위는 별도 확인 항목이다. 확인한 Git blob SHA는 d8cd7ac9b3538b2286501cb9b869e7df2200f53e이다. [n8ncheck 고정 커밋의 검사기](https://github.com/mewuto/n8ncheck/blob/3eced09b1f8c651191135e839c67529fe12f1844/src/nodes/bigquery/checker.ts)

n8ncheck의 Slack 사용자 검증 시나리오는 [JavaScript AST를 사용하는 검사기](https://github.com/mewuto/n8ncheck/blob/3eced09b1f8c651191135e839c67529fe12f1844/src/scenarios/slack-user-validation/validators/jscode-validator.ts)를 포함한다. 따라서 기존 도구 전체를 문자열 검색으로 설명하면 안 된다. RiskVoid의 고정 소스는 정규식 기반 sanitizer 탐지와 발견 시 심각도 감소를 구현한다. 이는 모든 경로의 안전을 확정하는 동작과 다르다. 같은 값에 적용된 검증, 다른 값 검증, 검증되지 않은 우회 분기, 변환 후 위험이 다시 생긴 경우를 각각 시험해야 우열을 판단할 수 있다.

비교 평가에서는 저장소 커밋, 도구·규칙 버전과 실행 설정을 고정하고 기록한다.

## 4. 공개 유통·연구·실제 악성 패키지의 근거 구분

### 4.1. AIronClaw의 n8n 템플릿 조사

AIronClaw는 n8n.io 조회수 상위 1,000개와 8개 GitHub 자료 집합을 포함해 12,750개 템플릿을 정적으로 검사했다고 보고했다. 34,880개는 정적 발견 항목의 수이며, 이 중 14개가 Critical로 분류됐다. 716개는 인증 전 고심각도(high-severity) SSRF 또는 SQL injection 경고가 하나 이상 있다고 정적으로 판정된 워크플로 수다. 개별 발견 항목 수나 모든 유형의 인증 전 위험을 합친 수가 아니다. 별도로 선택한 6개는 지정한 로컬 환경에서의 실행 결과를 보고한다. [AIronClaw 조사 방법과 결과](https://blog.aironclaw.com/n8n-12k-templates-critical-vulnerabilities/)

숫자는 표본 선정, 중복 제거, 정적 규칙과 선택 사례의 실행 조건 안에서 해석한다. 전체 생태계의 취약률과 운영 중 피해율은 대표 표본과 운영 증거가 필요하다. 도구 간 성능과 제품 수요는 비교 평가와 사용자 조사의 별도 질문이다.

글은 n8n 워크플로 검사기와 실제 고객에게 사용하는 규칙을 설명한다. 이는 제공자가 공개한 연구·운영 주장이다. 이 조사에서 해당 n8n 검사 서비스에 파일을 제출해 상용 API·UI의 동작이나 탐지율을 검증하지 않았다. MCP 제품 문서만 보고 n8n 연구 역량이 없다고 결론 내리지 않으며, 반대로 연구의 숫자를 상용 서비스 품질 보증으로 사용하지 않는다.

이 세 근거를 합쳐 “모든 공유 플랫폼에서 악성 워크플로가 유통된다”고 말할 수는 없다. 현재 가능한 설명은 **공개 공유 파일에서 검토할 위험 구조를 확인했고, 공개 템플릿의 격리 연구와 악성 의존성 배포의 별도 사례가 있다**는 것이다. 우리가 해결한다고 주장하려면 이 구조를 본뜬 합성 사례에서 탐지·정상 반례·수정 효과를 직접 검증해야 한다.

## 5. 검토가 있어도 위험이 계속 공유될 수 있는 이유

가능한 이유는 공개 자료와 검사 경계에서 도출한 설계상 추론이다. 실제 발생 빈도는 별도 평가 항목이다.

| 가능한 이유                  | 발생 조건                                                                          | 제품에 반영할 판단                                                         |
| ---------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 검토 범위와 배포 경로가 다름 | 공식 제출 가이드가 모든 개인 저장소·복사본에 적용되지는 않음                       | 출처와 검사 대상 파일을 명시하고 “공식·인기”를 안전성 근거로 대체하지 않음 |
| 환경이 달라짐                | 원래의 인증 앞단, 네트워크 제한, 계정 권한, 데이터 민감도가 가져오는 환경과 다름   | JSON에서 확인한 사실과 사용자 환경에서 확인할 조건을 분리                  |
| 일반 기능도 위험해질 수 있음 | HTTP·메일·SQL·명령 실행이 사용 목적·입력·권한에 따라 정상 작업 또는 위험 경로가 됨 | 기능 존재와 실제 위험 연결을 구분하고 정상 반례를 검증                     |
| 분석 한계가 있음             | 동적 표현식, 임의 Code, 미지원 노드, 제공되지 않은 하위 워크플로가 존재            | 분석 불가를 명시하고 경고가 없다는 이유로 안전 판단을 만들지 않음          |
| 복사·수정 후 근거가 달라짐   | 목적지·인증·권한이 바뀌거나 검사·리뷰가 다른 파일 버전을 가리킴                    | 새 Version 재검사, 보안 변화 비교, 배포 파일 일치 확인                     |

따라서 해결할 문제는 단순히 “검사를 추가한다”에 그치지 않는다. **무엇을 어디까지 확인했는지, 어떤 사용 조건이 남았는지, 수정·업데이트가 그 판단을 어떻게 바꾸는지**를 사용자가 다룰 수 있어야 한다는 가설이다.

## 6. Workflow Hub가 입증해야 할 다섯 가지 가설

| 가설                                           | 제안 기능                                                            | 비교에서 확인할 결과                                              | 현재 상태     |
| ---------------------------------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------------- | ------------- |
| H1. 근거 연결이 이해를 개선                    | 탐지를 노드·필드·입력 경로·필요 조치·미확인 조건에 연결              | 실행 주체·전송 대상·위험·조치의 정답률, 올바른 판단까지 걸린 시간 | 미구현·미측정 |
| H2. 자체 분석이 실질적 탐지를 개선             | 지원 노드 버전과 필드 흐름, 방어 조건, 분기·변환을 해석              | 기존 도구 대비 추가 정탐, 오탐·미탐 변화, 분석 불가 범위          | 미구현·미측정 |
| H3. 보안 의미의 비교가 업데이트 검토를 개선    | 목적지·인증·고권한 작업·입력 경로·분석 범위의 변화 표시              | 중요한 변화 발견률, 잘못된 승인·불필요한 거부, 검토 시간          | 미구현·미측정 |
| H4. 수정·재검사 연결이 실제 조치를 개선        | 수정안 미리보기, 새 Version, 같은 기준의 재검사, 정상 동작 검증 근거 | 위험 경로 해소와 정상 기능 보존을 동시에 달성한 비율              | 미구현·미측정 |
| H5. 특정 파일과 근거의 연결이 배포 실수를 줄임 | 불변 Version·파일 해시·검사·정책 평가·공개 파일 연결                 | 잘못된 파일·오래된 검사 결과 연결의 차단과 사용자 혼동 감소       | 미구현·미측정 |

H1과 H3는 근거를 이해하고 검토에 활용하는 경험을 측정한다. H2는 분석 엔진의 추가 기여를 평가한다. H4는 위험 해소와 정상 동작 보존을 함께 확인한다. H5의 파일 일치는 제품이 충족해야 할 정확성 기준이자 사용자 실수를 줄이는지 평가할 항목이다.

장기적으로 유지할 수 있는 강점의 후보는 검증된 노드·버전 어댑터, 반례와 수정 사례의 축적, 근거 추적과 조치 경험이다. 이 강점을 평가하려면 지원 범위와 검증 사례의 축적 결과가 필요하다.

## 7. 공정한 비교와 사용자 검증

### 비교군을 나눠 기여를 측정한다

| 비교군                           | 구성                                                          | 알 수 있는 것                                                 |
| -------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------- |
| A. 기존 도구의 정상 사용         | 문서가 권장하는 설정·출력·UI와 지원 기능 사용                 | 사용자가 실제 선택할 수 있는 기준선                           |
| B. 같은 탐지 + Workflow Hub 표현 | A와 동일한 탐지에 노드 위치, 중복 통합, 근거·조치 설명을 제공 | A→B는 이해·조치 선택의 개선. 자체 탐지 향상으로 계산하지 않음 |
| C. B + 자체 분석                 | 지원 범위의 n8n 필드 흐름·방어 조건·버전 해석을 추가          | B→C는 추가 탐지와 오탐·미탐 변화                              |
| D. C + 수정·버전 흐름            | 보안 변화 비교, 수정·재검사, 정확한 Version 공개·사용 연결    | C→D는 수정·업데이트·파일 선택 과정의 효과                     |

기준선에는 기존 도구에서 실제 사용 가능한 근거·조치·검토 기능을 포함한다. 기존 탐지와 자체 분석이 추가한 탐지를 각각 기록한다. 동일한 입력과 사용 가능한 정보를 기준으로 비교하고, 인스턴스 접속형과 파일 정적 검사형의 차이를 기록한다.

예를 들어 FlowGuard·n8ncheck·RiskVoid에서 지원하는 분석을 켜고, 비교 과제에 맞는 경우 0xCD4의 변경 검토·receipt와 n8n Workflow reviews의 버전 검토도 기준선 후보에 포함한다. 사용 가능한 기능을 일부러 끄거나 기존 보고서를 불리하게 축약하지 않는다. A는 하나의 임의 도구를 뜻하지 않는다. 과제별로 실제 사용 가능한 도구·설정·출력과 조합을 정하고 버전을 고정한 뒤 A→B→C→D를 비교한다. 상용 서비스에 접근하지 못한 경우 문서 비교와 실행 비교를 구분하고 성능 표에 실행값을 만들지 않는다.

A~C의 정량 탐지 비교는 공통 n8n 입력·라벨·실행 조건이 성립하는 도구와 사례에 한정한다. Make·Zapier의 공유 경험과 MCP 프록시 보안 서비스는 해당 사용 과제의 참고 비교로 구분하고, 서로 다른 검사 대상의 탐지율을 직접 순위로 매기지 않는다.

C→D는 여러 기능을 함께 추가한 전체 흐름의 효과다. H3·H4·H5 각각의 독립 효과를 주장하려면 기능별 과제를 따로 평가하거나, 해당 기능만 추가하는 비교를 수행한다.

### 평가 사례와 측정 원칙

규칙 개발용 사례와 최종 평가용 사례를 분리한다. 정상·위험·분석 불가 사례를 포함하고, 지원 노드·버전·입력 출처·위험 작업·방어 조건과 기대 결과를 먼저 정한다. 근거가 불확실한 사례를 정상으로 분류하지 않는다. 세부 합성 사례는 [보안 설계의 검증 계획](SECURITY_DESIGN.md#11-검증-계획과-완료-기준)을 따른다.

외부 공개 파일을 그대로 복제해 실제 계정·목적지에 연결하지 않는다. E-CV-6216·JAW 등에서 확인한 **문제 구조만 합성 워크플로로 재작성**하고, 가짜 문서·계정·DB·수신 endpoint를 사용한다. 원본 출처와 참고한 구조를 기록하되 원본의 개인정보·키·특정 목적지를 사례에 반입하지 않는다. 공개 소스 읽기와 팀 관리 합성 환경의 실행 검증을 구분하며, 사용자 업로드를 서버에서 실행하지 않는 원칙을 유지한다.

다음 사례군은 [보안 설계 11절](SECURITY_DESIGN.md#11-검증-계획과-완료-기준)의 `SEC-*` ID를 사용한다. 평가 manifest에서 같은 ID에 `R`(명시한 환경의 위험), `N`(같은 업무 목적의 정상 반례), `U`(의미·의존성 부족으로 판단 유보) 변형을 연결하는 제안이다. 모든 노드·버전의 지원을 미리 약속하는 표가 아니며, `U` 변형은 `SEC-UNKNOWN-01/02`와 중복 집계하지 않고 교차 참조한다.

| `SEC-VERSION-04`, `SEC-ENV-01`          | `v1→v1.1`에서 인증을 제거하거나 외부 전송·고권한 작업을 추가한다.                                                  | 위치·설명 변경 등 보안 의미가 유지되는 갱신이다.                                           | 외부 변수·자격증명·하위 워크플로 변경 정보가 없다. 중요 변화·비중요 변화·미확인을 별도 정답으로 정한다.            |
| `SEC-INTEGRITY-01/02`, `SEC-FAILURE-01` | 다른 파일 해시·다른 버전·임대 만료 후 재배정 전/후의 작업 시도·다른 규칙 결과를 제출하거나 이전 결과를 재사용한다. | 정확히 요청한 Version·해시·검사·정책에 연결된 결과와 파일을 사용한다.                      | 실패·시간 초과·부분 분석인 검사다. 공개 판단과 검사 프로세스 종료를 구분하고 거부·검토 사유를 확인한다.            |

각 사례의 manifest에는 `case_id`, 참고 근거 ID, 합성 파일 해시, n8n/노드/패키지 버전, 연결 자원, 환경 전제, 정책, 예상 source·sink·방어 조건, 정답·판정 단위, 정상 출력·허용 부작용, 개발/최종평가 구분을 기록한다. `R` 라벨은 팀 관리 실행 근거 또는 독립 검토된 성립 조건과 연결하며, 그 조건이 없는 실행에서는 위험을 확정한 결과로 집계하지 않는다.

- 탐지 항목의 일치·중복 기준을 먼저 정한다. 같은 경로의 경고를 여러 개 세어 성능을 부풀리지 않는다.
- 평가 가능한 발견 항목의 정밀도, 사전 선언한 지원 범위 내 양성 사례의 재현율, 전체 양성 사례 중 발견 비율을 구분한다. 공통 지원 사례에서는 동일한 라벨 단위로 정탐·오탐·미탐을 비교한다.
- 정상 사례의 오탐률, 미지원·불확실·실패·시간 초과의 수와 비율을 별도로 보고한다. 지원하기로 한 사례의 실행 실패를 재현율 분모에서 빼지 않는다.
- 도구·규칙·커밋·실행 옵션·시간·자원 한도를 기록한다. 같은 조건에서 다시 실행할 수 있어야 한다.
- 최종 사례와 라벨에는 구현 외의 검토를 포함한다. 의견이 갈린 사례와 결과의 적용 범위를 기록한다.

수정 성공은 **명시한 합성 환경에서 위험 경로가 제거되고, 원래 의도한 결과와 허용된 부작용이 보존되는 것**으로 정의한다. 검증은 팀 관리 합성 워크플로와 테스트 전용 서비스에서 수행한다.

### 가설별 분모·실패 처리·산출물

| 대상                     | 평가 단위·분모                                                                                                                                                                                                            | 측정·실패 처리                                                                                                                                                                                   | 보존할 산출물과 사전 성공 기준                                                                                                                                                         |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| H2 탐지                  | 라벨 단위는 `사례·위험유형·source/sink 경로 또는 설정 위치`로 정규화한다. 정밀도 분모는 중복 제거된 평가 가능 경고, 재현율 분모는 사전 선언한 지원 범위의 양성 라벨이다. 전체 양성 라벨에 대한 발견 비율도 따로 보고한다. | 정상 반례의 오탐, 미지원률, 분석 실패·시간 초과·부분 결과를 별도로 보고한다. 지원한다고 선언한 양성에서 실패해 찾지 못한 것은 분모에서 제거하지 않는다. 판단 불가를 음성/안전으로 바꾸지 않는다. | 고정 도구/규칙·원출력·정규화 결과·라벨 검토·혼동행렬·실패 목록. 추가 정탐의 최소 개선과 허용 오탐 변화, 지원 범위·성능/자원 한도를 실행 전에 정한다.                                   |
| H1 이해·H3 업데이트 판단 | 참가자에게 배정된 사례별 질문·검토 과제가 분모다. 실행 주체·전송 대상·위험·필요 조치·미확인 조건, 중요 변화 승인/거부 정답을 미리 작성한다.                                                                               | 정답률·완료시간과 잘못된 승인·불필요한 거부·미확인을 안전으로 오해한 비율을 구분한다. 중도 포기·시간 초과·미응답을 제외해 정답률을 높이지 않고 별도 실패로 보고한다.                             | 익명 과제 응답·시간 기록·정답 근거·경험 수준·할당 순서. 최소 판단 개선, 시간 효과, 허용 오판 변화와 참가자 수 근거를 평가 전에 정한다.                                                 |
| H4 수정                  | 배정된 위험 수정 과제 전체가 분모다. 도구가 수정안을 못 낸 경우도 포함한다.                                                                                                                                               | 같은 기준의 재검사, 공격 조건 차단, 정상 입력의 기대 출력·허용 부작용 보존을 모두 만족해야 성공이다. 경고만 사라짐, 전체 기능 비활성화, 테스트 실패·미실행·시간 초과는 성공으로 계산하지 않는다. | 변경 diff·새 Version/해시·전후 검사·합성 정상/공격 실행 결과·기능 회귀 목록. 최소 복합 성공률 개선과 허용 기능 회귀 범위를 사전에 정한다.                                              |
| H5 배포·근거 연결        | `SEC-INTEGRITY-01/02`·`SEC-FAILURE-01`의 예정된 정상/불일치/실패 상태 주입 시도 전체 및 사용자 파일 선택 과제 전체를 각각 분모로 둔다.                                                                                    | 불일치 결과의 수락, 오래된 시도의 최신 결과 덮어쓰기, 다른 파일 제공은 정확성 실패다. 정상 요청 거부·검사 실패의 안전 표시·시도 누락도 따로 보고한다.                                            | Version·해시·작업시도·규칙/정책 버전·검사·공개/다운로드 매핑과 마스킹된 감사 이벤트. 정해진 일치 조건을 어긴 수락·파일 제공이 없어야 하는 불변조건과 사용자 혼동 개선 목표를 구분한다. |

목표 수치·표본 수는 이 문서에서 임의로 정하지 않는다. 대신 실행 전에 `평가 계획 고정본`에 사례 집합과 제외 조건, A~D의 실제 구성·버전·옵션, H1~H5별 1차 지표, 필요한 개선 폭·허용 악화 폭, 표본 수 근거, 자원·시간 한도, 분석 방법·불확실성 표시와 성공/실패 판정식을 확정한다. 결과를 본 뒤 문턱이나 분모를 바꾸면 탐색적 결과로 표시하고 독립 사례에서 다시 평가한다. 기준을 확정하지 않은 예비 실행은 성공 입증으로 보고하지 않는다.

제안하는 평가 산출물은 계획 고정본, 사례 manifest와 파일 해시, 독립 라벨 검토 기록, A~D 원출력·정규화 결과, 합성 실행의 정상/공격 결과, 전후 Version 비교, 익명 사용자 과제 결과, 실패·미지원 목록, 재현 절차다. 이 문서 작성 시 해당 비교 실행·사용자 시험을 수행한 것은 아니다.

### 사용자 검증

사용자는 전송 대상, 실행 가능한 사람, 위험 작업, 필요한 변경, 남은 미확인 조건을 판단하는 과제를 수행한다. 정답과 완료 시간을 함께 기록하며, 잘못된 승인·불필요한 거부·미확인을 안전으로 오해한 경우를 구분한다. n8n 경험 수준을 기록하고 비교 순서를 조정해 학습 효과를 줄인다.

구현 전에는 현재 검토 방식과 어려움, 최근 실제 사용 사례, 업로드 의향을 인터뷰로 확인할 수 있다. 구현 후에는 A~D의 사용 과제와 실제 수정·재검사 완료를 비교한다. 참가자 수·목표 수치·성공 기준은 평가 설계 때 사전에 정한다.

자체 분석의 추가 가치가 확인되지 않으면 H2의 우월성 주장을 철회하고 H1·H3·H4의 제품 가치에 집중할 수 있다. 사용자 이해와 조치에도 개선이 없다면 기능 추가보다 문제 정의와 대상 사용자를 재검토한다.
