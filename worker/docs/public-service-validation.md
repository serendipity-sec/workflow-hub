# 실제 공개 n8n 데이터의 서비스 적합성 검증

2026-11-22, 엔진 `0.3.0` / 커밋 `93555be80ac21c0e5c1f36a55205c860c70cb77a`의 워커를 실제 공개 n8n JSON에 실행했다. 결론은 **검토 보조용 검사 기반은 동작하지만, 아래 두 서비스 흐름을 완결된 기능으로 제공하기에는 아직 부족하다**는 것이다. 이번 변경은 검증 하네스·실측 기록·판정 문서이며, 발견한 제품 결함을 수정한 구현은 아니다.

1. 미리 검사한 워크플로의 기능·위험·분석 범위를 설명하고 다운로드 제공.
2. 사용자 수정본을 검사하고 수정안/수정본·재검사·원본과 비교·버전별 다운로드 제공.

## 입력과 실제 실행

공식 n8n API의 공개 템플릿 15개를 목적별로 선정했다. 5개는 같은 날 수집했던 고정 원본을 재사용했고, 10개는 이번 검증에서 추가 수집했다. 통계적 표본이나 취약점 정답 데이터가 아니므로 정확도·재현율을 계산하지 않았다. 공개/심사 상태를 안전의 정답으로 사용하지 않았다.

새 입력은 `https://api.n8n.io/templates/workflows/{id}` 응답의 `workflow.workflow` 객체를 JSON으로 추출했다. 응답 원본 해시와 실제 검사한 추출 바이트 해시를 별도로 기록했다. 노드·코드·표현식·연결을 수정하지 않았으며 수집/직렬화 방식과 재사용 여부를 기록했다. 원본 파일·응답·상세 보고서는 로컬 `.runtime/n8n-service-validation-20261122/`에만 보관한다. 라이선스/재배포 허용은 확인하지 않았으며 원본을 저장소에 올리거나 웹에 공개하지 않았다.

고정 이미지 `sha256:76a440f2875efc886561396555a44f19ed06fa549ee152d13ab6aefeb6368c3e`에서 실제 Gitleaks·Presidio·spaCy·AST 검사를 실행했다. 네트워크·파일 쓰기·권한·자원 제한은 기존 `assess` 경로와 동일하다. 외부 워크플로·Code·표현식·SQL·설정된 외부 API는 실행하지 않았다. 실행 의미/정상 업무 보존은 이번 시험에서 검증하지 않았다.

| 실측                           | 결과                                                            |
| ------------------------------ | --------------------------------------------------------------- |
| 공식 원본 JSON                 | 15개                                                            |
| 검사 결과                      | `partial` 14개, `error/invalid_input` 1개, `analyzed` 0개       |
| 검사에 진입한 파일의 도구 실행 | 42회 완료, 도구 오류 0개. 입력 거부 1개는 도구 검사를 받지 않음 |
| 자동 수정 계획                 | 원본 15개에서 0개                                               |
| 수동 수정/비교 시험            | 실제 원본에서 만든 통제된 변경 3개 확인, 원본 해시 유지         |
| 정책/배포/키/정상 동작         | 실제 운영 정책·자격 증명·권한·업무 실행은 확인하지 않음         |

`partial`은 실패 자체를 뜻하지 않는다. 다만 해당 파일 전체를 확인했다고 말할 수 없고, 누락 위치와 기능을 사용자에게 보여야 한다. 정책을 제공하지 않았으므로 `inconclusive`라는 정책 결론 역시 예상된 동작이다. 이번 평가에서 중요한 것은 그 상태를 구성하는 실제 미지원·오탐·호환성 문제다.

548개 관찰 기록에는 정상적인 인증/SQL 작업/외부 전송 기능도 포함된다. 351개 수동 계획도 351개 취약점이라는 뜻이 아니다. 원문에는 정보성 관찰에서도 계획을 생성하는 현상이 있어, 웹에서 finding/plan 개수를 위험 개수로 표시하면 오해를 만든다.

## 수정→재검사→비교 시험

[실제 실행 기록](../validation/public-service-path-results.json)은 실제 원본에서 만든 다음 **통제된 수정본** 3개다. 자연 발생한 사용자 파일이나 원래 템플릿에서 발견한 추가 위험 사례로 집계하지 않는다.

1. 10111의 인증 기본값을 `headerAuth`로 변경: 재검사에서 인증 기본값 후보가 사라지고 인증 설정 관찰이 생기며 `authentication_changed`를 기록했다. 자격 증명은 제공하지 않았으므로 실제 인증 집행은 미검증이다. 비교 역시 이를 완전히 해결된 위험으로 승인하지 않는다.
2. 7643의 Slack 수신자를 합성 식별자로 변경: 재검사하고 `recipient_changed`를 인식했다. 수신자 원문은 공개 요약에 남기지 않았다.
3. 7643의 Slack 전송을 비활성화: `node_disabled`로 기능 변화를 인식했다. 정상 기능 보존/보안 수정 성공을 주장하지 않는다.

그러나 `compare-static`은 기존 base v2 규칙만 비교한다. `assess`의 확장 13개 규칙·하위 파일을 통합한 finding 변화 비교는 현재 없다. `diff-definitions`는 선언의 의미 변화이며 그 공백을 대신하지 않는다. 따라서 새 PII/Python/SQL/전송 분석의 위험이 생겼는지·지속되는지·더는 관찰되지 않는지를 제품 전체에 일관되게 표시하는 부분은 미완성이다.

## 두 서비스 흐름에 대한 판정

| 서비스 역할              | 현재 상태                                                                            | 필요한 작업                                                                      |
| ------------------------ | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| 미리 원본 검사           | 지원 범위의 정적 검사·격리·마스킹·해시 연결은 동작                                   | ID 없는 입력 수용, 실제 주요 노드/버전 지원, 구체적인 오류와 누락 위치           |
| 기능·위험·분석 범위 설명 | 위험/범위의 고정 코드와 위치는 있음. 기능 요약 계약은 없음                           | 워커의 trigger→처리→출력 구조화 근거와 서비스의 사람이 읽는 설명·노드 표시 연결  |
| 위험 수정본 제공         | 수동 지침과 TLS/좁은 PG 2.8 자동 수정 2종. 이 실제 원본 15개에는 자동 적용 대상 없음 | 지원 범위를 명시한 수정 생성과 검토, 불확실한 수정은 수동 처리, 별도의 동작 확인 |
| 원본/수정본 재검사·비교  | 재검사·해시·선언 변화는 동작, base finding 비교 있음                                 | 전체 assessment 위험 비교·규칙/범위 축소 구분·자식 파일 대응                     |
| 공개·버전 다운로드       | 워커가 승인/저장을 수행하지 않음                                                     | 서비스가 정확한 파일/검사 버전·공개 범위·권한·다운로드 바이트 연결을 검증        |

제품에 붙이기 전 워커 우선 보완은 다음 순서가 적절하다.

1. **진입 호환성과 진단:** ID 없는 정식 템플릿, 구체적인 오류/위치와 합성 ID 안정성.
2. **사용자가 보는 근거의 신뢰도:** UUID/enum/기술 메타데이터의 NLP 오탐, 정보성 관찰과 수정 필요 후보 구분, 불필요한 수동 수정 계획 정리.
3. **전후 위험 비교 완성:** 확장 규칙·하위 파일을 포함한 `assess` 비교.
4. **실제 핵심 경로 확대:** PG 2.4/문자열 바인딩/복잡한 SQL, Notion/Docs/WhatsApp/직접 Gemini와 필요한 Code 출력의 필드 추적.
5. **설명과 수정의 제품 계약:** 기능 구조 요약, 근거 연결, 지원 범위별 수정본 생성/검토·동작 검증 상태.

실제 팀 API 연동은 이번에도 제외했다. API가 준비되는 것만으로 위 워커 품질·비교·수정 문제가 해결되지는 않는다. 반대로 부분 분석을 명확히 보여 주는 선별 템플릿의 전문가 검토 보조 흐름에는 현재 결과를 활용할 수 있다.

## 재현

Node.js 24와 기존 통합 검사 이미지를 준비한 뒤 `worker/`에서 아래 명령을 실행한다. 원본 데이터 디렉터리는 같은 출처의 `downloads.json`, 숫자 ID의 `.workflow.json`을 포함해야 하며 각 바이트/해시가 일치해야 한다. 새 수집이면 그 시점의 해시/결과가 달라질 수 있다.

```text
node validation/verify-public-assessment.mjs <download-directory> validation/public-assessment-results.json
node validation/verify-public-service-paths.mjs <download-directory> <comparison-output>
```

첫 명령이 만든 상세 보고서는 원본 디렉터리에 저장된다. 두 번째 명령은 그 보고서의 해시를 확인한 뒤 새 수정본 파일만 생성하며 원본을 보존한다. 공개 파일·개인정보·자격 증명 원문을 fixture나 커밋에 넣지 않는다.

첫 명령은 기존 격리 실행 영수증의 이미지 ID와 현재 빌드 해시를 대조한다. 다른 이미지를 사용할 경우 먼저 `verify-assessment-runtime.mjs`로 검증하고 그 결과 경로를 `WORKER_ASSESSMENT_RUNTIME_RECEIPT`로 지정한다. 비교 명령도 기준/수정 보고서 스키마와 기준 이미지 ID를 확인한다. 하네스 리뷰에서 이 기준 이미지 확인 누락을 찾아 보완했으며, 실제 비교 3건 재실행과 다른 이미지의 기준 보고서를 시작 전에 거부하는 부정 사례를 확인했다. 워커 `npm run verify` 217개와 루트 계약·도구 검사 6개도 통과했다.
