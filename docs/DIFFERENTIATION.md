# 차별화 근거와 검증 계획

> 팀 검토용 제안 · 자료 확인일 2026-11-21 (한국 시간)

## 1. 현재 내릴 수 있는 결론

기존 플랫폼과 도구는 보안 감사, 템플릿 제출 검토, 노드 관계 분석, 버전 승인, 공유·설정 안내를 이미 제공한다. 관련 보안 서비스에는 검사 결과에서 완화와 재검증으로 이어지는 흐름도 있다. 이 기능들을 비교의 출발점으로 삼는다. Workflow Hub의 효과는 6절의 가설을 평가한 결과로 설명한다.

Workflow Hub의 제안은 **외부 n8n 파일을 가져오는 사용자가 노드별 위험 근거와 분석 한계를 이해하고, 수정 전후의 보안 변화를 확인하며, 검사한 정확한 리비전을 선택해 사용할 수 있게 하는 것**이다. 이 흐름이 기존 도구의 정상적인 사용보다 판단과 조치를 개선하는지는 별도 평가가 필요하다.

이 문서는 경쟁 기능의 조사, 제품 가설, 입증 방법을 관리한다. 구현 방법은 [SECURITY_DESIGN.md](SECURITY_DESIGN.md), 시스템 경계는 [ARCHITECTURE.md](ARCHITECTURE.md), 단계와 결정 상태는 [PLAN.md](PLAN.md)에서 관리한다. 현재 상태는 기능 설계와 평가 계획 단계다.

## 2. 누구의 어떤 문제를 검증할 것인가

우선 대상은 다른 사람이 만든 n8n 템플릿을 자신의 계정·DB·업무 데이터에 연결하는 사용자다. 다음 대상은 이를 배포하는 제작자와 팀 검토자다. 사용자의 개발 경험은 평가에서 구분한다.

검증하려는 문제는 다음과 같다.

- 가져온 파일에서 실행 주체, 전송 대상, 위험 작업과 필요한 권한을 파악하기 어려운가?
- 경고를 읽어도 어떤 노드와 값을 바꿔야 하는지 판단하기 어려운가?
- 업데이트가 목적지·인증·권한·입력 흐름을 어떻게 바꾸는지 놓치는가?
- 경고를 없애는 과정에서 원래 업무 동작을 망가뜨리거나, 검사한 파일과 다른 파일을 사용하는가?
- 개인정보나 업무 구조를 담은 파일을 별도 플랫폼에 업로드할 의향이 있는가?

문제의 빈도와 심각도, 현재 해결 방식, 제품 전환·지불 의사는 검증할 가설이다. 사용자 수요와 사업성은 사용자 조사에서 확인한다.

#### 코드에서 얻은 구체적인 검증 후보

검토한 FlowGuard 입력 검증 규칙은 노드 유형을 기준으로 그래프 경로를 판단한다. 해당 함수에서 값과 검증 조건의 의미까지 확인하는 분석은 미확인이다. 입력 검증이 실제 작업 값과 연결되는지, 관련 분기에 적용되는지, 이후 값이 변하는지 합성 사례로 비교한다. 관찰한 범위는 한 규칙의 소스다. 전체 도구의 탐지 성능은 고정한 설정에서 별도로 측정한다. 확인한 Git blob SHA는 4f47f2b3ad543157f95db2dac040c258f4855a83이다. [FlowGuard 고정 커밋의 규칙](https://github.com/MohibShaikh/FlowGuard/blob/03b348d008eaafdebc3650973561d8091af1d8c8/src/rules/owasp/missing-input-validation.ts)

n8ncheck에서 확인한 BigQuery 검사 파일은 BigQuery·BigQueryTool의 설정과 동적 쿼리 구성을 다룬다. DB별 비교 평가에서는 동적 구성, 값 바인딩, 입력 출처를 각각 확인한다. 다른 DB 노드와 시나리오의 지원 범위는 별도 확인 항목이다. 확인한 Git blob SHA는 d8cd7ac9b3538b2286501cb9b869e7df2200f53e이다. [n8ncheck 고정 커밋의 검사기](https://github.com/mewuto/n8ncheck/blob/3eced09b1f8c651191135e839c67529fe12f1844/src/nodes/bigquery/checker.ts)

비교 평가에서는 저장소 커밋, 도구·규칙 버전과 실행 설정을 고정하고 기록한다.

## 4. 사용자가 제시한 AIronClaw 글의 해석

AIronClaw는 n8n.io 조회수 상위 1,000개와 8개 GitHub 자료 집합을 포함해 12,750개 템플릿을 정적으로 검사했다고 보고했다. 34,880개는 정적 발견 항목의 수이며, 이 중 14개가 Critical로 분류됐다. 요약에서 인증 전 도달 가능으로 분류한 716개는 정적 판정이다. 별도로 선택한 6개는 지정한 로컬 환경에서의 실행 결과를 보고한다. [AIronClaw 조사 방법과 결과](https://blog.aironclaw.com/n8n-12k-templates-critical-vulnerabilities/)

숫자는 표본 선정, 중복 제거, 정적 규칙과 선택 사례의 실행 조건 안에서 해석한다. 전체 생태계의 취약률과 운영 중 피해율은 대표 표본과 운영 증거가 필요하다. 도구 간 성능과 제품 수요는 비교 평가와 사용자 조사의 별도 질문이다.

## 5. 검토가 있어도 위험이 계속 공유될 수 있는 이유

가능한 이유는 공개 자료와 검사 경계에서 도출한 설계상 추론이다. 실제 발생 빈도는 별도 평가 항목이다.

| 가능한 이유                  | 발생 조건                                                                          | 제품에 반영할 판단                                                         |
| ---------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 검토 범위와 배포 경로가 다름 | 공식 제출 가이드가 모든 개인 저장소·복사본에 적용되지는 않음                       | 출처와 검사 대상 파일을 명시하고 “공식·인기”를 안전성 근거로 대체하지 않음 |
| 환경이 달라짐                | 원래의 인증 앞단, 네트워크 제한, 계정 권한, 데이터 민감도가 가져오는 환경과 다름   | JSON에서 확인한 사실과 사용자 환경에서 확인할 조건을 분리                  |
| 일반 기능도 위험해질 수 있음 | HTTP·메일·SQL·명령 실행이 사용 목적·입력·권한에 따라 정상 작업 또는 위험 경로가 됨 | 기능 존재와 실제 위험 연결을 구분하고 정상 반례를 검증                     |
| 분석 한계가 있음             | 동적 표현식, 임의 Code, 미지원 노드, 제공되지 않은 하위 워크플로가 존재            | 분석 불가를 명시하고 경고가 없다는 이유로 안전 판단을 만들지 않음          |
| 복사·수정 후 근거가 달라짐   | 목적지·인증·권한이 바뀌거나 검사·리뷰가 다른 파일 버전을 가리킴                    | 새 리비전 재검사, 보안 변화 비교, 배포 파일 일치 확인                      |

따라서 해결할 문제는 단순히 “검사를 추가한다”에 그치지 않는다. **무엇을 어디까지 확인했는지, 어떤 사용 조건이 남았는지, 수정·업데이트가 그 판단을 어떻게 바꾸는지**를 사용자가 다룰 수 있어야 한다는 가설이다.

## 6. Workflow Hub가 입증해야 할 다섯 가지 가설

| 가설                                           | 제안 기능                                                           | 비교에서 확인할 결과                                              | 현재 상태     |
| ---------------------------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------- | ------------- |
| H1. 근거 연결이 이해를 개선                    | 탐지를 노드·필드·입력 경로·필요 조치·미확인 조건에 연결             | 실행 주체·전송 대상·위험·조치의 정답률, 올바른 판단까지 걸린 시간 | 미구현·미측정 |
| H2. 자체 분석이 실질적 탐지를 개선             | 지원 노드 버전과 필드 흐름, 방어 조건, 분기·변환을 해석             | 기존 도구 대비 추가 정탐, 오탐·미탐 변화, 분석 불가 범위          | 미구현·미측정 |
| H3. 보안 의미의 비교가 업데이트 검토를 개선    | 목적지·인증·고권한 작업·입력 경로·분석 범위의 변화 표시             | 중요한 변화 발견률, 잘못된 승인·불필요한 거부, 검토 시간          | 미구현·미측정 |
| H4. 수정·재검사 연결이 실제 조치를 개선        | 수정안 미리보기, 새 리비전, 같은 기준의 재검사, 정상 동작 검증 근거 | 위험 경로 해소와 정상 기능 보존을 동시에 달성한 비율              | 미구현·미측정 |
| H5. 특정 파일과 근거의 연결이 배포 실수를 줄임 | 불변 리비전·파일 해시·검사·정책 평가·공개 파일 연결                 | 잘못된 파일·오래된 검사 결과 연결의 차단과 사용자 혼동 감소       | 미구현·미측정 |

H1과 H3는 근거를 이해하고 검토에 활용하는 경험을 측정한다. H2는 분석 엔진의 추가 기여를 평가한다. H4는 위험 해소와 정상 동작 보존을 함께 확인한다. H5의 파일 일치는 제품이 충족해야 할 정확성 기준이자 사용자 실수를 줄이는지 평가할 항목이다.

장기적으로 유지할 수 있는 강점의 후보는 검증된 노드·버전 어댑터, 반례와 수정 사례의 축적, 근거 추적과 조치 경험이다. 이 강점을 평가하려면 지원 범위와 검증 사례의 축적 결과가 필요하다.

## 7. 공정한 비교와 사용자 검증

### 비교군을 나눠 기여를 측정한다

| 비교군                           | 구성                                                          | 알 수 있는 것                                                 |
| -------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------- |
| A. 기존 도구의 정상 사용         | 문서가 권장하는 설정·출력·UI와 지원 기능 사용                 | 사용자가 실제 선택할 수 있는 기준선                           |
| B. 같은 탐지 + Workflow Hub 표현 | A와 동일한 탐지에 노드 위치, 중복 통합, 근거·조치 설명을 제공 | A→B는 이해·조치 선택의 개선. 자체 탐지 향상으로 계산하지 않음 |
| C. B + 자체 분석                 | 지원 범위의 n8n 필드 흐름·방어 조건·버전 해석을 추가          | B→C는 추가 탐지와 오탐·미탐 변화                              |
| D. C + 수정·리비전 흐름          | 보안 변화 비교, 수정·재검사, 정확한 리비전 공개·사용 연결     | C→D는 수정·업데이트·파일 선택 과정의 효과                     |

기준선에는 기존 도구에서 실제 사용 가능한 근거·조치·검토 기능을 포함한다. 기존 탐지와 자체 분석이 추가한 탐지를 각각 기록한다. 동일한 입력과 사용 가능한 정보를 기준으로 비교하고, 인스턴스 접속형과 파일 정적 검사형의 차이를 기록한다.

A~C의 정량 탐지 비교는 공통 n8n 입력·라벨·실행 조건이 성립하는 도구와 사례에 한정한다. Make·Zapier의 공유 경험과 MCP 프록시 보안 서비스는 해당 사용 과제의 참고 비교로 구분하고, 서로 다른 검사 대상의 탐지율을 직접 순위로 매기지 않는다.

C→D는 여러 기능을 함께 추가한 전체 흐름의 효과다. H3·H4·H5 각각의 독립 효과를 주장하려면 기능별 과제를 따로 평가하거나, 해당 기능만 추가하는 비교를 수행한다.

### 평가 사례와 측정 원칙

규칙 개발용 사례와 최종 평가용 사례를 분리한다. 정상·위험·분석 불가 사례를 포함하고, 지원 노드·버전·입력 출처·위험 작업·방어 조건과 기대 결과를 먼저 정한다. 근거가 불확실한 사례를 정상으로 분류하지 않는다. 세부 합성 사례는 [보안 설계의 검증 계획](SECURITY_DESIGN.md#11-검증-계획과-완료-기준)을 따른다.

- 탐지 항목의 일치·중복 기준을 먼저 정한다. 같은 경로의 경고를 여러 개 세어 성능을 부풀리지 않는다.
- 평가 가능한 발견 항목의 정밀도, 사전 선언한 지원 범위 내 양성 사례의 재현율, 전체 양성 사례 중 발견 비율을 구분한다. 공통 지원 사례에서는 동일한 라벨 단위로 정탐·오탐·미탐을 비교한다.
- 정상 사례의 오탐률, 미지원·불확실·실패·시간 초과의 수와 비율을 별도로 보고한다. 지원하기로 한 사례의 실행 실패를 재현율 분모에서 빼지 않는다.
- 도구·규칙·커밋·실행 옵션·시간·자원 한도를 기록한다. 같은 조건에서 다시 실행할 수 있어야 한다.
- 최종 사례와 라벨에는 구현 외의 검토를 포함한다. 의견이 갈린 사례와 결과의 적용 범위를 기록한다.

수정 성공은 **명시한 합성 환경에서 위험 경로가 제거되고, 원래 의도한 결과와 허용된 부작용이 보존되는 것**으로 정의한다. 검증은 팀 관리 합성 워크플로와 테스트 전용 서비스에서 수행한다.

### 사용자 검증

사용자는 전송 대상, 실행 가능한 사람, 위험 작업, 필요한 변경, 남은 미확인 조건을 판단하는 과제를 수행한다. 정답과 완료 시간을 함께 기록하며, 잘못된 승인·불필요한 거부·미확인을 안전으로 오해한 경우를 구분한다. n8n 경험 수준을 기록하고 비교 순서를 조정해 학습 효과를 줄인다.

구현 전에는 현재 검토 방식과 어려움, 최근 실제 사용 사례, 업로드 의향을 인터뷰로 확인할 수 있다. 구현 후에는 A~D의 사용 과제와 실제 수정·재검사 완료를 비교한다. 참가자 수·목표 수치·성공 기준은 평가 설계 때 사전에 정한다.

자체 분석의 추가 가치가 확인되지 않으면 H2의 우월성 주장을 철회하고 H1·H3·H4의 제품 가치에 집중할 수 있다. 사용자 이해와 조치에도 개선이 없다면 기능 추가보다 문제 정의와 대상 사용자를 재검토한다.
