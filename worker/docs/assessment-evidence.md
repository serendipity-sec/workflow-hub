# 정책·환경·의존성 근거 계약

이 문서는 #14에서 추가한 `assess` 계층의 로컬 계약이다. 기존 `scan` v2와 SQL v1 기록은 유지한다. 팀 API·공개 권한 계약을 확정하는 문서가 아니다.

## 입력과 신뢰 경계

`assessment-evidence.ts`의 sidecar `schemaVersion: "1.0.0"`는 검사할 **원본 바이트 SHA-256**에 연결된다. 업로드 JSON의 정책·메모·주석을 이 입력으로 승격하지 않는다. 호출자가 별도로 제공한 정책도 인증된 서비스 권한으로 간주하지 않는다.

| 필드                    | 제공할 내용                                                        | 해석과 한계                                                                                        |
| ----------------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| `sources`               | 식별자, 선언/제공된 관측, 방법, 기록 시점, 관측 자료 해시          | `supplied_observation`에는 자료 해시가 필요하다. 서명·수집 경로를 워커가 독립 검증한 것은 아니다.  |
| `provenance`            | 출처 URL·플랫폼·template ID·고정 commit·수집 시점·라이선스 근거    | 출처 정보를 보존한다. URL 방문이나 재배포 권한 확인은 실행하지 않는다.                             |
| `policy`                | 목적, 규칙별 심각도 기준, 허용/금지 목적지, 데이터 분류, 예외      | 파일의 기술적 탐지와 정책 판단을 분리한다.                                                         |
| `runtime`               | n8n 버전, 환경 식별자, 자격 증명 범위, 네트워크 통제, 앞단 인증    | 선언된 사실로 보고한다. 인증 선언으로 파일의 무인증 Webhook 경고를 지우지 않는다.                  |
| `packages`·`advisories` | 실제 패키지 이름·버전·연결 노드·선택적 무결성 값, 제공된 OSV 문서  | `typeVersion`을 npm 버전으로 대체하지 않는다. 네트워크 조회나 패키지 설치를 하지 않는다.           |
| `subworkflows`          | 부모 파일 해시·호출 노드·참조·정확한 자식 버전·원본 JSON·자식 해시 | 파싱 전에 크기와 해시를 확인한다. 재귀 분석기는 참조/호출 노드/순환/깊이를 추가 확인한다.          |
| `classifications`       | 노드와 필드에 부여한 데이터 분류, 출처                             | 이름에서 추정한 민감도와 별도로 취급한다.                                                          |
| `aiApprovals`           | Agent와 도구 노드별 승인 요구 선언                                 | 실제 승인 실행이나 모델의 공격 저항성은 미확인이다.                                                |
| `syntheticReceipts`     | 파일 해시·환경·시점·출처·사례별 공격 차단과 정상 동작 결과         | 두 결과를 각각 보존한다. 다른 파일의 영수증은 `other_file`이며 워커의 실행 결과로 계산하지 않는다. |
| `publicationReview`     | 정확한 파일·정책 버전·검토자·기간·노출 검토 범위                   | 공개 후보의 로컬 선행 조건이다. 실제 공개 승인이나 다운로드 권한은 서비스가 확인한다.              |

전체 sidecar는 1 MiB, JSON 깊이는 48, 출처 64개, 패키지 64개, advisory 128개, 자식 8개, 자식당 256 KiB, 분류 256개, 승인 64개, 영수증 16개(각 32사례)로 제한한다. UTF-8 오류·중복 JSON 키(escape로 표현한 같은 키 포함)·알 수 없는 필드·중복 적용 범위·존재하지 않는 출처를 거부한다. 부모별 자식 호출을 구별하며, 자식 분석 시 부모 노드 분류/승인/공개 검토를 자동 상속하지 않는다.

출력은 전체 입력 해시, 마스킹된 식별자, 고정된 근거 코드와 시점을 사용한다. 원문 주소·수신자·목적·쿼리·패키지 설명을 복사하지 않는다. `evidenceSummarySchema`, `policyEvaluationSchema`, `dependencyResultsSchema`는 이 출력의 strict 스키마다.

## 정책 평가와 공개 전 검토

`assessDestination`은 같은 전송 사실에 별도 정책을 적용한다. HTTP는 사용자 정보가 없는 `http(s)` origin으로 비교한다. 이메일은 표시 이름 없는 단일 주소, Slack/Telegram은 호출자가 확인한 안정 식별자, 응답은 `caller`, 실행 로그는 `execution_log`를 사용한다. 동적 목적지·알 수 없는 분류·정책 누락은 `unknown`이며 정당한 전송을 악의로 판정하지 않는다.

`evaluatePolicy`는 `allow / review / block / inconclusive`를 반환한다. 실패한 분석이나 미지원 범위는 허용의 근거가 아니다. 예외는 finding ID·정확한 입력 해시·주체·사유 코드·출처·활성 기간에 한정하며 원래 finding을 삭제하지 않는다. 오탐 검토와 위험 수용을 구분한다.

공개 후보에는 성공한 분석, 정책 허용, 현재 파일/정책에 대한 미만료 검토가 필요하다. 비밀정보·개인정보·내부 주소·계정 참조의 네 검토 범위를 모두 요구하며 정책에서 이 선행 검토를 끌 수 없다. 비밀정보 후보는 단순 위험 수용으로 공개 가능해지지 않는다. 재배포 제한이 선언되면 거절한다. 충족해도 결과는 `eligible_for_service_review`이고 실제 서비스 인증·권한·불변 파일 선택은 남는다.

## OSV와 AI 지원 범위

OSV의 npm `SEMVER` 및 npm `ECOSYSTEM` 범위와 명시적 버전 목록을 비교한다. `introduced`는 포함, `fixed`/`limit`는 제외, `last_affected`는 포함하며 여러 구간과 prerelease를 다룬다. GIT 범위·잘못된 버전/구간·철회된 문서·자료 누락은 미확인이다. `not_affected`는 **제공된 snapshot 안에서만** 해당하며 알려지지 않은 취약점이나 악성 코드를 배제하지 않는다. [OSV 공식 형식](https://ossf.github.io/osv-schema/)을 기준으로 하며 OSV-Scanner 실행을 가장하지 않는다.

AI 검사는 `ai_languageModel`·`ai_tool` 연결과 상류 입력 경로, Code/명령/HTTP/하위 워크플로 등 도구 기능, 도구별 승인 선언을 고정 코드로 기록한다. 일반 연결은 제어 경로 근거이며 모델에 전달된 값 전체를 증명하지 않는다. 승인 선언이 있어도 실제 집행과 프롬프트 인젝션 저항성은 미확인이다. 기능 해석은 [n8n Custom Code Tool](https://docs.n8n.io/integrations/builtin/cluster-nodes/sub-nodes/n8n-nodes-langchain.toolcode), [Call n8n Workflow Tool](https://docs.n8n.io/integrations/builtin/cluster-nodes/sub-nodes/n8n-nodes-langchain.toolworkflow) 공식 설명과 구분해 기록한다.

## 유한한 완료 판정표

다음은 [보안 설계 11절](../../docs/SECURITY_DESIGN.md#11-검증-계획과-완료-기준)의 전체 25개 사례를 워커가 수행할 부분과 서비스/실행 근거가 필요한 부분으로 나눈 범위다. 새 모듈의 통합 검증 결과는 별도 실행 기록을 기준으로 한다. 범위 밖 결과를 정상으로 채우거나, 문서의 기능을 일괄적으로 후속 과제로 제외하지 않는다.
