# 개발 목표와 실행 계획

> 상태: 팀 검토용 제안. 보안 검사와 리비전 관리를 연결하는 제품 범위와 구현 순서를 제안한다.

## 1. 제품 목표

다른 사람이 만든 n8n 워크플로를 가져와 사용하려는 사람이 동작, 위험 근거, 사용 조건을 이해하고, 수정본의 검사 이력을 비교한 뒤 특정 버전을 선택할 수 있게 한다.

기존의 개인 비공개 업로드·리비전·다운로드 흐름을 기반으로 다음 경험을 연결하는 것을 제안한다.

1. JSON을 업로드하고 불변 리비전을 생성한다.
2. 비동기 검사 결과에서 확인된 설정, 위험 경로, 분석하지 못한 부분을 확인한다.
3. 노드·필드·데이터 흐름을 통해 근거를 이해한다.
4. 수정안을 적용하거나 수정본을 업로드해 새 리비전을 만든다.
5. 재검사와 보안 변화 비교로 수정 효과와 새 위험을 확인한다.
6. 정책과 사용 조건에 맞는 특정 리비전을 공개·다운로드·재사용한다.

서비스 배포를 위해 Supabase PostgreSQL과 실행 환경을 준비한다. 검사 범위, 자동 수정, 공개 정책은 해당 구현 단계에 맞춰 결정한다.

### 차별화 근거와 검증

n8n의 보안 감사·템플릿 검토·버전 리뷰, 공개 검사기의 노드·시나리오 분석, 관련 서비스의 완화·재검증을 비교 기준으로 삼는다. 검증할 가설은 근거 이해, 자체 분석의 추가 탐지, 보안 변화 파악, 정상 동작을 유지하는 수정, 검사한 파일의 정확한 선택이다. 공식 자료의 범위와 비교군 A~D의 구성은 [DIFFERENTIATION.md](DIFFERENTIATION.md)에서 관리한다. 제품 구현, 도구 비교, 사용자 평가의 결과를 각각 기록한다.

## 2. 기존 계획과의 관계

이전 계획은 4명이 9~10일 동안 개인 업로드·수정 계보·다운로드 데모를 만드는 기반 작업이었다. 보안 규칙·자동 수정·공개 공유는 당시 필수 범위에서 제외했다.

이번 문서는 그 기반 위에 보안 검사와 리비전 활용을 핵심 사용자 흐름으로 추가하는 확장안이다. 이전 일정은 기반 작업의 이력으로 보존하며 새 범위의 기한으로 재사용하지 않는다. 새 일정과 담당자는 단계별 범위·완료 조건을 팀이 검토한 뒤 정한다.

### PostgreSQL 기반 작업

초기 작업 범위는 Spring 서비스의 PostgreSQL 연결, 버전 관리 마이그레이션, 권한 분리와 환경별 검증이다. Spring JDBC·PostgreSQL 드라이버, Flyway, Data API에 노출하지 않는 서비스 스키마를 후보로 검토한다. 서비스 계정은 런타임에 필요한 권한을 갖고 스키마 변경은 별도 마이그레이션 역할에서 수행한다. 도메인 테이블과 저장 기능은 후속 이슈의 범위다.

- 실제 PostgreSQL의 빈 DB에 초기 마이그레이션을 적용하고 재실행 시 중복 변경이 없는지 통합 테스트로 확인한다. 사용할 DB 버전과 로컬 검증 구성은 개발용 Supabase 환경에 맞춰 정한다.
- 런타임 역할의 정상 연결과 DDL 권한 거부를 확인한다. 연결 및 마이그레이션 실패를 오류로 기록한다.
- 개발용 Supabase에서 배포 환경에 맞는 연결 경로, 서버 인증서를 검증하는 TLS, 역할별 권한을 확인한다. 로컬과 실제 개발 환경의 결과를 각각 기록한다.
- 비밀값 없이 설정과 확인 절차를 [SETUP.md](SETUP.md)에 정리한다.

실제 스키마는 구현 이슈에서 추가하는 마이그레이션을 기준으로 한다. 구현 API 계약은 코드와 함께 `contracts/openapi.yaml`에 반영한다.

## 7. 완료를 판단하는 기준

- 리비전 파일과 검사 대상이 같은 바이트임을 서버에서 확인한다.
- 리비전·결과·수정안·다운로드를 다른 사용자 식별자로 요청해도 접근할 수 없다.
- 검사 실패·시간 초과·필수 미지원 경로를 문제 없음으로 표시하지 않는다.
- 탐지 결과는 노드·필드와 근거 수준을 포함하고 비밀정보가 마스킹된다.
- 지원 범위의 정상·위험·미지원 합성 사례에서 기대 결과를 확인한다.
- 같은 사례에서 기존 탐지와 자체 분석의 추가 탐지·오탐·미탐을 기록한다.
- 근거 화면·보안 변화·수정 흐름의 효과는 사용자 판단의 정확도와 실제 조치 완료로 평가한다. 기능 구현과 비교·사용자 평가의 결과를 각각 기록한다.
- 수정 후 같은 규칙 기준으로 비교하고, 지원 테스트에서 원래 업무 동작을 확인한다.
- 공개 파일과 검사 파일이 일치하며 비공개 부모·결과가 자동 노출되지 않는다.
- 실제 외부 연동과 배포에서 확인하지 못한 사항을 완료 보고에 남긴다.

검사 품질은 항목별 오탐·미탐과 분석 불가 범위를 분리해 확인한다. 발견 개수나 하나의 안전 점수로 품질을 판단하지 않는다. 고정된 정확도·성능 목표는 평가 데이터와 실행 조건을 정한 뒤 합의한다.

## 8. 팀 역할 제안

실제 담당 배정은 팀이 확정한다. 공통 파일은 한 담당자가 편집하고 계약 변경은 영향을 받는 담당자와 검토한다.

| 역할          | 주요 책임                                                             |
| ------------- | --------------------------------------------------------------------- |
| Backend/Infra | 데이터·소유권·파일 저장, 검사 작업·결과, 배포·외부 연동               |
| Frontend      | 대표 사용자 흐름, 노드 근거, 상태·미확인 표시, 보안 변화·수정·공개 UI |
| Security A    | n8n 정규화·노드 버전 어댑터·흐름·방어 조건 해석                       |
| Security B    | 도구·규칙 연동, 합성 사례·반례, 탐지와 수정 효과 평가                 |

기획과 설계 대안은 대화·검토 과정에서 정리하고, 채택한 결과는 저장소 문서와 이슈에 남긴다. Codex는 이슈와 문서에 기록된 범위로 구현·검증한다. 작업 시작·마무리·GitHub 게시 절차와 스킬 경로는 현행 [AGENTS.md](../AGENTS.md)를 따른다.
