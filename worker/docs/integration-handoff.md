# 초기 검사 결과와 서비스 연결 자료

작업 추적은 [#14](https://github.com/serendipity-sec/workflow-hub/issues/14), 실제 서비스 적응·통합 검증은 [#18](https://github.com/serendipity-sec/workflow-hub/issues/18)이다. 기존 워커 브랜치의 0.9.0·0.10.0 결과를 연결할 때 사용할 자료이며 팀 API를 임의로 확정한 문서가 아니다. 프론트·백엔드가 구현한 방식에 워커를 맞춘다.

## 워커 호출과 결과

신규 서비스 진입점은 `node dist/cli.js inspect <workflow.json> [evidence.json] [--llm]`이다. 기존 `assess`·`scan`·초기 SQL 명령과 과거 검증 이력은 호환/재현을 위해 보존한다. 신규 서비스가 초기 SQL 전용 `mock-once`를 10개 항목 통합 검사로 사용하면 안 된다.

프로그램 진입점은 `src/service/inspection.ts`의 `inspectFile`, 이미 검사한 결과 표시에는 `presentInspection`이다. 결과는 `inspectionSchema`로 검증한다.

0.9.0·0.10.0은 서비스 묶음·설명을 1.1.0으로 제공하고(`0.10.0`은 `serviceScope`에 `sinkReachableGapCount`·`isolatedGapCount` 도달성 집계를 추가), 과거 0.8.0 및 이전 보고서는 1.0.0 표시를 재현한다. `coverage <assessment.json> [inspection.json]`의 [원인 분류 결과](coverage-causes.md)는 환경·정의 누락·검사기 확장·혼합 원인·지원 범위를 구분하며 원래 판정을 바꾸지 않는다. 1.1.0 화면 분류도 같은 원인 등록부를 사용한다. [0.10.0 성능·범위 기록](performance-and-scope-0.10.0.md)을 함께 참고한다.

| 필드                       | 의미                                                                     |
| -------------------------- | ------------------------------------------------------------------------ |
| `inspectionVersion: 1.1.0` | 엔진 0.9.0·0.10.0의 서비스 전달용 묶음 버전                              |
| `inputSha256`              | 검사한 정확한 원본 바이트의 SHA-256                                      |
| `assessment`               | 10개 범주의 원본 정적 검사·위치·근거·오류·범위·수정 계획                 |
| `serviceReport`            | 고정 한국어 기능 설명, 위험 후보와 관찰, 분석 공백, 환경 확인, 지원 범위 |
| `llm`                      | 선택적 보조 설명 또는 미실행/실패 원인. 검사 판정을 바꾸지 않음          |

원본과 서비스 설명, LLM 문맥은 같은 파일·검사 결과에 결합되며 스키마가 재계산해 검증한다. 모델 설명은 부분 선택한 근거에만 연결한다. 공백 없는 JSON 직렬화 기준으로 전체 결과 약 6MiB를 수용하도록 설계하되 실제 API의 제한과 저장 방식을 확인해 어댑터를 맞춘다. 들여쓰기가 있는 CLI 출력은 더 커질 수 있으므로 기계 전달 시 공백 없는 직렬화와 실제 바이트 수를 사용한다. 검사 입력·도구 제한은 [assessment.md](assessment.md)를 따른다.

## 프론트 표시 원칙 — 항목 4의 워커 출력

1. **어떤 기능인가:** `functions`의 활성 노드 기능과 연결 근거를 표시한다. 실제 업무 목적·실행 성공을 추측하지 않는다.
2. **무엇을 확인/수정할까:** `findings`의 위치·이유·조치·수정 조건을 표시한다. `observations`는 일반 기능 관찰이며 취약점 수로 더하지 않는다.
3. **어디까지 검사했나:** `analysisGaps`는 실제 미지원/한도/누락 정의, `environmentChecks`는 사용 전 주의사항, `scopeNotes`는 개인정보 문맥 모델의 언어·완전성 등 범위 안내다. 실행 환경·권한·정책을 사용자 필수 입력으로 요구하지 않는다. 기존 개인정보·키·민감정보 탐지는 유지한다.
4. **실행 상태:** `executionStatus=completed`와 `analysisStatus=complete`면 “초기 정적 검사 범위 완료”로 표시할 수 있다. `securityReviewRequired=true`면 위험 또는 분석 공백의 검토를 함께 표시한다. `analysisStatus=review_required`면 “검사 완료 · 추가 보안 검토 필요”다. 어느 경우도 초록색 안전 보증으로 바꾸지 않는다. 도구 실패는 `completed_with_errors`, 입력/실행 실패는 `failed`다.
5. **LLM:** `generated`면 “AI가 고른 주요 확인 항목”으로 별도 표시하고 근거 참조를 제공한다. 모델은 기존 근거를 최대 8개 선택하고 워커가 고정 설명을 작성한다(`method: model_selection_with_deterministic_text`). 없으면 고정 설명을 표시한다. 결과는 평문으로 렌더링한다.
6. **수정·재검사:** 지원 수정만 새 파일로 만들고 새 버전으로 등록한다. 이전 승인·근거는 새 해시에 자동 승계하지 않는다. `compare-assessment`와 `diff-definitions` 결과로 경고 변화와 기능/범위 감소를 구분한다.

원시 `partial`은 원본 검사 이력에 보존하고 화면에는 선언한 서비스 범위의 상태를 표시한다. 환경 주의와 문맥 모델 완전성만으로 미완료 처리하지 않지만, 치명적일 수 있는 미해석 경로나 이미 발견한 위험을 범위 밖으로 빼지 않는다. `serviceScope`의 전체 수와 `omitted`를 함께 사용해 카드 한도에서 생략된 위험도 안내한다. 한국어 개인정보 모델 확대는 이번 사용자 결정에 따라 진행하지 않았다.

## 백엔드와 맞출 지점

0.7.0 검증 당시 2026-11-23 조회한 main `42e54e9`에는 업로드·목록/상세·버전·다운로드·비교/등록 및 원본 SHA-256/바이트 수 기록 코드가 있었다. 0.8.0 작업의 리뷰 기준 main은 `71e3108`이다. 이 워커 브랜치에 해당 팀 변경을 임의 병합하지 않았다. 원격 코드 존재는 배포 환경의 연동 검증과 다르다. 기존 `contracts/openapi.yaml`을 최신 main 계약으로 제시하지 않으며 실제 컨트롤러/OpenAPI 산출물을 확인한다.

실제 검사 작업 전달·상태·결과 수락에 해당하는 구현은 이번 코드 조회에서 확인하지 못했다. 다음은 요청할 정보와 연결 검증 기준이다.

- 실제 버전 ID·원본 파일 접근 방식·바이트 해시·크기를 워커에 어떻게 전달할지. 소유권은 인증된 서비스에서 확인한다.
- 검사 요청·작업 전달·상태·결과 저장 방식, 워커 인증, 재시도·취소·중복·지연 결과 처리를 실제 구현에 맞춰 확인한다. 기존 mock lease 계약을 강제하지 않는다.
- 동일 버전·동일 파일 해시에 원본 검사, 서비스 설명, 선택적 LLM 설명을 저장한다. 다른 파일의 결과를 수락하지 않는다.
- 수정본은 불변 새 버전으로 등록하고 재검사 결과와 비교 이력을 연결한다. 다운로드 바이트와 검사 해시가 일치해야 한다.
- 키는 워커 제어 프로세스의 비밀 설정에 둔다. 브라우저·분석 컨테이너·업로드 파일에 넣지 않는다. 외부 LLM 전송 범위는 별도 제품 정책으로 확인한다.
- 실제 배포에서 시간/CPU/메모리/PID/네트워크 격리·실패·취소·정리를 검증한다. 로컬 Docker 통과를 운영 완료로 처리하지 않는다.

아직 실제 팀 API 호출이나 화면 E2E를 완료하지 않았다. 연결 요청을 전달할 때는 새 커밋·검증 기록과 남은 분석 범위, 실제 LLM 시험 범위를 함께 제공한다. 모든 종류의 n8n workflow를 완전 분석한다는 전제는 사용하지 않는다.
